# codex responses 流式断连修复方案

## 背景与问题

codex 0.145.0 经 model_proxy 跨协议转换（responses→anthropic 上游）流式请求时，每次报 `stream disconnected before completion` 并重连 5 次后失败。根因已确认：`ModelProxyHandler` 未设 `protocol_version`（默认 HTTP/1.0），但流式 SSE 用 `Transfer-Encoding: chunked` 分帧——HTTP/1.0 + chunked 是非标准组合，codex 的 Rust hyper 客户端不认，chunked 帧字节混入 SSE 数据流导致解析失败→断连。详见 [[2026-08-17-codex-responses流式断连根因诊断]]。

本方案给出完整修复设计。

## 方案设计

### 改动点清单

| # | 文件:行号 | 改什么 | 优先级 |
|---|----------|--------|--------|
| 1 | core/server.py:1204（类属性区） | 加 `protocol_version = "HTTP/1.1"` | P0 主修复 |
| 2 | core/server.py:1204（类属性区） | 加 `timeout = 30` | P1 防御 |
| 3 | core/server.py:2308-2310 | `_write_translated_stream` except BrokenPipe 块补 finalize | P2 辅助 |
| 4 | core/server.py:2363-2365 | `_write_responses_stream` except BrokenPipe 块补 finalize | P2 辅助 |
| 5 | core/server.py:2415-2416 | `_write_translated_stream_from_responses` except BrokenPipe 块补 finalize | P2 辅助 |

---

### 1. protocol_version = "HTTP/1.1"（主修复）

**改动位置**：`core/server.py` L1204，`ModelProxyHandler` 类体内、`log_message` 方法之前。

```python
class ModelProxyHandler(BaseHTTPRequestHandler):
    """HTTP 请求处理器。…"""

    protocol_version = "HTTP/1.1"
    timeout = 30

    # 屏蔽默认日志
    def log_message(self, fmt, *args):
        pass
```

**为何一行够用**：

HTTP/1.1 引入的义务是：响应必须有 `Content-Length` 或 `Transfer-Encoding: chunked` 标记结束（否则 keep-alive 下客户端挂起）。逐一核实所有响应路径：

| 响应路径 | 方法 | 结束标记 | HTTP/1.1 安全 |
|----------|------|----------|--------------|
| 非流式 JSON（control API） | `_send_json`（L2517-2523） | `Content-Length: str(len(data))` | 安全 |
| 非流式缓冲响应 | `_write_buffered_response`（L2223-2237） | `Content-Length: str(len(body))` | 安全 |
| 内建非流式回执 | `_write_builtin_buffered_response`（L2065-2084）→ 调 `_write_buffered_response` | 间接有 Content-Length | 安全 |
| 透传流式 | `_write_streaming_response`（L2177-2221） | `Transfer-Encoding: chunked` + `0\r\n\r\n` 终止符 | 安全 |
| 转换流式（3 条路径） | `_write_translated_stream` / `_write_responses_stream` / `_write_translated_stream_from_responses` | 经 `_begin_sse_chunked` 发 `Transfer-Encoding: chunked` + `0\r\n\r\n` | 安全 |
| 内建流式回执 | L2056-2063，经 `_begin_sse_chunked` | 同上 | 安全 |

所有路径均有正确的结束标记，HTTP/1.1 下不会挂起。

**BaseHTTPRequestHandler 在 HTTP/1.1 下的行为**：
- `handle_one_request` 循环在 keep-alive 下继续等待下一请求（`close_connection` 默认 False）
- 客户端发 `Connection: close` 时自动设 `close_connection = True`，单请求后关连接
- ThreadingHTTPServer 每连接一线程，keep-alive 不阻塞其他请求

**`timeout = 30`**：HTTP/1.1 keep-alive 下空连接不主动关闭会占线程。设 30 秒 timeout，socket 超时后 `handle_one_request` 返回，连接关闭。30 秒远大于 LLM 单请求耗时，不影响正常请求。

### 2. finalize 移入 except BrokenPipe 块（辅助修复）

**问题**：三个转换流式方法中，`adapter.finalize()` 和 chunked 终止符 `0\r\n\r\n` 在 try 块内。BrokenPipe 时被跳过，导致 adapter 状态机未收尾。

**关键洞察——usage=0 的真正根因**：

`usage_in` / `usage_out` 在 `adapter.feed()` 过程中从 `message_delta` 事件赋值（translate.py L1512-1518）。`usage_tuple()` 在 try 块外执行（server.py L1916），不受 BrokenPipe 影响。usage=0 的原因是**断连太早**（HTTP/1.0 chunked 导致 codex 第一个 chunk 就断连），此时上游 `message_delta` 事件尚未到达，adapter 内部 usage 本就是 0。修复 protocol_version 后断连不再发生，usage 自然恢复。**usage 提取逻辑本身无独立 bug，不需额外修。**

但 finalize 结构仍有缺陷：即便断连与 usage 无关，adapter 状态机未收尾会导致 `response.completed` 事件不发，日志观测不完整。

**修复方式**：在每个方法的 `except (BrokenPipeError, ConnectionResetError):` 块内补调 `finalize()` + 写终止符，用 try-except 包裹 write。成功路径不变（try 块内已调 finalize，幂等不会重发）。

以 `_write_responses_stream`（L2329-2378，codex 实际走的路径）为例：

```python
# 现状（L2363-2365）
except (BrokenPipeError, ConnectionResetError):
    # 客户端已断开，写不进去也无所谓，静默即可
    pass

# 修复后
except (BrokenPipeError, ConnectionResetError):
    # 客户端断连：仍尝试 finalize 收尾（幂等，write 失败无所谓）
    try:
        for ev in adapter.finalize():
            self._write_sse_chunk(pt.responses_sse_bytes(ev))
        self.wfile.write(b"0\r\n\r\n")
        self.wfile.flush()
    except (BrokenPipeError, ConnectionResetError, OSError):
        pass
```

同样模式应用于 `_write_translated_stream`（L2308-2310）和 `_write_translated_stream_from_responses`（L2415-2416），各自用对应的 `pt.anthropic_sse_bytes` 替换 `pt.responses_sse_bytes`。

**为何不改 finally**：三个方法已有 `finally: upstream_resp.close()`。如果把 finalize 移入 finally，成功路径会调两次 finalize（try 块一次 + finally 一次），虽然幂等不会重发事件，但会让成功路径写两次 `0\r\n\r\n`（第二次写到已发完的流上可能无害但不干净）。在 except BrokenPipe 块内补调是最小改动、最清晰的方案。error 路径（except Exception）不调 finalize（当前设计如此，避免在失败态伪造收尾），保持不变。

### 4. 回归风险

#### 非流式响应（最大回归点）

| 客户端 | 当前（HTTP/1.0） | 修复后（HTTP/1.1） | 影响 |
|--------|-----------------|-------------------|------|
| curl 探针 | HTTP/1.0 + Content-Length → 连接关闭结束 | HTTP/1.1 + Content-Length → keep-alive | 无影响：curl 正确处理 Content-Length |
| claude code SDK | 同上 | 同上 | 无影响 |
| codex（非流式） | 同上 | 同上 | 无影响 |

**关键验证**：`_send_json`（L2517-2523）和 `_write_buffered_response`（L2223-2237）都显式设了 `Content-Length`。HTTP/1.1 下客户端靠 Content-Length 判定响应结束，不靠连接关闭。无挂起风险。

#### 流式响应（透传 + 转换）

`_write_streaming_response`（L2190）和 `_begin_sse_chunked`（L2258）都设了 `Transfer-Encoding: chunked`。HTTP/1.1 + chunked 是标准组合（RFC 7230 §4.1），所有 HTTP/1.1 客户端正确处理。这是修复的核心——从非标准组合（HTTP/1.0 + chunked）变为标准组合。

#### keep-alive 线程泄露

HTTP/1.1 默认 keep-alive，空连接会占线程。`timeout = 30` 防御：socket 超时后 `handle_one_request` 返回 False，`handle` 循环退出，连接关闭。30 秒不影响正常请求（LLM 单请求远超 30 秒，但 keep-alive 等待的是请求间空闲期，不是请求本身）。

#### control API

`_send_json` 有 Content-Length，HTTP/1.1 下安全。control API 客户端（CLI/status）会正确处理 keep-alive。

## 风险与权衡

1. **protocol_version 升级风险极低**：所有响应路径都有正确的结束标记，这是 HTTP/1.1 的唯一硬性要求。ThreadingHTTPServer 多线程模型不受 keep-alive 影响。

2. **finalize 辅助修复是防御性的**：修复 protocol_version 后 codex 不再断连，finalize 结构缺陷不再被触发。但修复它能让未来万一再断连时 adapter 状态机正确收尾、日志完整。

3. **不动 usage 统计逻辑**：确认 usage=0 是断连太早导致 message_delta 未到达，不是提取逻辑 bug。protocol_version 修复后自然恢复。如修复后仍有 usage=0，再排查 adapter 的 message_delta 事件解析。

4. **timeout=30 可能偏短**：如果未来有长轮询或 SSE 推送场景（持续数十秒无数据），30 秒会断连。当前 model_proxy 是同步请求-响应模式，无此场景。如需调整，改类属性即可。

## 验证方式

### 修复前对照（已在前一轮诊断完成，此处不重复）

### 修复后验证

1. **类属性**：`python3 -c "from core.server import ModelProxyHandler; print(ModelProxyHandler.protocol_version, ModelProxyHandler.timeout)"` → `HTTP/1.1 30`

2. **raw TCP 捕获**：起 model_proxy，用 raw socket 发 `POST /v1/responses HTTP/1.1`，捕获响应首行 → 确认 `HTTP/1.1 200 OK`

3. **codex 端到端**：`codex exec` 跑一个简单 prompt → 确认不再报 `stream disconnected before completion`

4. **日志**：检查 model_proxy access 日志，确认 `source=responses` 流式请求 `usage_in≠0, usage_out≠0, stop_reason=end_turn`

5. **非流式回归**：`curl -s http://127.0.0.1:18889/v1/messages -d '{"model":"...","messages":[...]}'` → 确认正常返回（有 Content-Length，不挂起）

6. **control API 回归**：`curl -s http://127.0.0.1:18889/model_proxy/status -H "X-Proxy-Admin-Token: ..."` → 确认正常返回

7. **单测**：`cd tools/model_proxy && python3 -m unittest tests.test_protocol_version -v` → 全绿

8. **已有测试回归**：`python3 -m unittest discover tests/ -v` → 全绿（特别是 test_passthrough_sniff 和 test_cooldown_rules）
