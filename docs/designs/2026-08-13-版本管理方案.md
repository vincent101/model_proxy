# model_proxy 版本管理方案

## 背景

model_proxy 当前无显式版本号：
- `history_versions/` 目录存 v1 下线归档（`proxy-v1-archived-20260724.tar.gz` + ARCHIVE_README.txt），是"大版本下线归档"实践，但无版本号字段。
- 外层 vault repo 有 git tag `pre-data-storage-cleanup-20260808`，是 vault 全库 tag，非 model_proxy 专属。
- README.md 有 frontmatter（`created: 2026-07-17`），无 `version` 字段。
- `core/server.py` 里的 `"version": 3` 是 totals 账本 schema 版本，与产品版本无关。
- 无 VERSION 文件、无 CHANGELOG、无 `__version__`。

需求：当前版本定为 V0.9，设计轻量版本管理机制。未来计划用 repo-split 拆成独立 git repo，版本方案需为拆分留好接口。

## 设计

### 1. 版本号载体：三件套

| 载体 | 内容 | 作用 | 真相源 |
|------|------|------|--------|
| `VERSION` 文件（根目录纯文本） | `0.9` | 脚本/运行时可读，最权威 | **主** |
| git tag | `v0.9` | git 层面快照，可回溯 | 镜像 |
| README frontmatter `version` | `0.9` | 给人看，Obsidian 可读 | 镜像 |

**单一真相源 = VERSION 文件**。tag 和 frontmatter 是它的镜像，发版时三处同步更新。

**为什么 VERSION 文件是主而非 tag**：tag 在拆分前属于外层 vault repo，拆分后才属于 model_proxy 独立 repo。VERSION 文件始终属于 model_proxy 目录，拆分时随 history 完整迁移，不受 repo 归属变化影响。拆分后 tag 才能真正打在 model_proxy 自己的历史上。

**一致性维护**：发版时一个动作更新 VERSION 文件 → 同步改 README frontmatter → 打 git tag。三处不一致时以 VERSION 文件为准（脚本可校验）。

### 2. 版本号规范

**不强制 semver，用简化两段式**：`MAJOR.MINOR`（如 `0.9`、`0.10`、`1.0`）。

- `MINOR` 递增（0.9 → 0.10 → 0.11）：功能新增、行为改进、配置 schema 兼容扩展（如本次 cooldown 策略组）。
- `MAJOR` 递增（0.x → 1.0）：破坏性变更——协议重构、配置 schema 不兼容、入口/端口变更。触发 1.0 时，旧版本按 `history_versions/` 实践归档。
- **不设补丁位**（不写 0.9.1）：补丁即 MINOR 递增，避免三段式维护负担。若未来确需补丁位再引入。
- `V` 前缀：VERSION 文件和 frontmatter 写**纯数字** `0.9`（不带 V，便于脚本解析）；git tag 带 `v` 前缀 `v0.9`（git 惯例，区分 tag 与分支名）。

**与 `history_versions/` 的边界**：
- `history_versions/` = 大版本下线归档（v1 下线 → tar.gz 封存）。
- 版本号 = 小版本递增追踪。
- 两者配合：日常 MINOR 递增改 VERSION；MAJOR 跳变（如 1.0 → 2.0）时，把旧版归档进 `history_versions/` 再升 MAJOR。

### 3. 变更记录：CHANGELOG.md

**要**，轻量。根目录 `CHANGELOG.md`，格式：

```markdown
# Changelog

## 0.9 (2026-08-13)
- 新增 cooldown_rules 策略组（按 errorcode 分组冷却 + failover，URLError sentinel）
- 402 额度耗尽进 failover 白名单，6h 冷却
- /model_proxy/status 新增 unconfigured_codes 暴露未配策略的 code

## 0.8 (2026-08-xx)
- ...
```

- 只记"用户可感知的变化"（功能、配置、行为），不记纯重构。
- 每次升版本号时追加一条，不强制每次 commit 都记。
- 与 git log 互补：git log 是细粒度历史，CHANGELOG 是人读的版本摘要。

### 4. 运行时可见性：暴露到 /model_proxy/status

**要**。`/model_proxy/status` 增加 `version` 字段，读 VERSION 文件（启动时读一次缓存，非每请求读盘）。

实现：
- `core/server.py` 启动时读 `VERSION` 文件内容，存模块级常量 `_VERSION`。
- `_handle_status` 响应 JSON 增加 `"version": "0.9"`。
- VERSION 文件不存在时 `_VERSION = "unknown"`，不阻断启动。

收益：用户 `curl status` 一眼看到当前跑的版本，排障时对照 CHANGELOG 知道有哪些变更。

### 5. 现有 tag 处置

`pre-data-storage-cleanup-20260808` 是外层 vault repo 的 tag，记录的是 vault 全库状态，**不迁移**到 model_proxy。拆分后 model_proxy 独立 repo 从 `v0.9` 起建 tag，与外层 tag 无关。

### 6. 与 repo-split 的衔接

- VERSION 文件、CHANGELOG.md、README frontmatter 都在 model_proxy 目录内，repo-split 的 history 模式会随 subtree split 完整迁移到内层 repo。
- 拆分后在内层 repo 打 `v0.9` tag（拆分前打在外层无意义，拆分后历史归 model_proxy 自己）。
- 拆分前先落地 VERSION 文件，这样它进入迁移历史，而非拆分后补加。

### 7. 落地清单

| # | 文件（绝对路径） | 动作 | 内容示意 |
|---|------|------|----------|
| 1 | `tools/model_proxy/VERSION` | 新建 | `0.9` |
| 2 | `tools/model_proxy/CHANGELOG.md` | 新建 | 0.9 条目（cooldown 策略组等） |
| 3 | `tools/model_proxy/README.md` | 改 frontmatter | 加 `version: 0.9` |
| 4 | `tools/model_proxy/core/server.py` | 改 | 启动读 VERSION 存 `_VERSION`；`_handle_status` 加 `version` 字段 |
| 5 | `tools/model_proxy/config/model_proxy_config.example.json` | 不动 | — |

**执行顺序**（分两阶段）：

- **拆分前**（在 vault 外层 repo 内）：1 (VERSION) → 2 (CHANGELOG) → 3 (README frontmatter) → 4 (server.py 读版本) → 跑测试验证。这些文件随 repo-split history 模式迁移进内层 repo。
- **拆分后**（model_proxy 独立 repo 内）：打 `v0.9` tag。

**为什么 tag 必须在拆分后**：拆分前 model_proxy 是 vault 外层 repo 的子目录，`git tag v0.9` 会打在 vault 全库 commit 上，标签指向 vault 状态而非 model_proxy 专属状态，且 subtree split 不迁移外层 tag。拆分后 model_proxy 有独立 git 历史，此时打 tag 才指向 model_proxy 自己的 commit。

## 风险

1. **三处漂移**：VERSION / frontmatter / tag 不一致。缓解：以 VERSION 为准，发版时同步更新；可写校验脚本但非必须（人肉同步即可，发版频率低）。
2. **CHANGELOG 维护负担**：可能忘记记。缓解：只在升版本号时记一条，不强制每 commit；漏记可后补。
3. **运行时读 VERSION 失败**：文件被误删。缓解：`_VERSION = "unknown"` 兜底，不阻断服务。

## 开放问题（需用户拍板）

1. **版本号格式**：`0.9`（纯数字，推荐）vs `V0.9`（带 V 前缀）？git tag 用 `v0.9`。
2. **是否要 CHANGELOG**：推荐要（轻量），还是觉得多余先不要？
3. **status 暴露 version**：推荐要，还是纯 git 层面管理不暴露到运行时？
4. **MAJOR/MINOR 触发判定**：cooldown 改造算 MINOR（0.9），未来什么变更算 MAJOR？是否接受"协议重构/配置不兼容才 MAJOR"的简单规则？
