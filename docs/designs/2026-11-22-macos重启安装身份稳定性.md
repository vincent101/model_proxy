# macOS 重启后安装身份稳定性：卷 UUID + inode 身份契约（理想 root-cause 设计草案）

## 背景与问题

### 目标与边界

用户在 macOS 重启后遇到 model_proxy 因安装身份校验无法启动/查询。目标：**重启不再导致已有安装被判定为变更**，同时保留确有必要的单实例锁、账本/记录保护与控制凭据边界。

本步只做实证调查与设计：未改代码/配置/身份记录/进程，未提交 git，未重启设备。方案已于 2026-11-22 经用户确认；实现由主会话另行派单，本文档不含实施。

### 已验证事实（含证据定位）

### 推断（标注依据，不当作已验证）

- I1：F1 证明**至少一次跨启动间 st_dev 变化且 inode 不变**。不能据此断言 18:25 这次重启是唯一原因；但同一路径、同一 inode、不同 device 的组合，与“目录被替换/移动”应有的 inode 变化不符，故“device 不稳定导致身份校验失败”是当前最强解释。
- I2：APFS 卷 UUID 是落盘元数据，按设计跨重启稳定；本会话**未跨重启实测**该 UUID。擦除/恢复/迁移会改变它——那属于真实安装变化，应走显式恢复，不应静默接受。
- I3：Windows 启动路径不存在同类跨重启持久身份比较，故不受本 bug 影响；但静态阅读发现 `core/cli/windows_control.py:293` 的 `validate_record_claim` 要求 `schema==2`，而 Windows 服务写 `schema==3`（`core/server.py:5125`）。该路径可达性未实测，**单列为待验证项，不并入本方案根因**。

### 待验证/未定位

- Q1：那次 `on` 的 `preflight_changed` 具体抛出点。现有证据（无时间戳、无 CLI 日志）不足以归因；不应写成“重启导致”。诊断建议：CLI 错误输出保留安全 code（已含该 code），并在后续实现中为各 preflight 阶段加不泄密的阶段标记。
- Q2：本机卷 UUID 跨真实重启的稳定性（I2）——需真机验收，见“验证方式”。
- Q3：HFS+ 路径在本机无样本，只按 API 契约设计，需注入测试。
- Q4：Windows `validate_record_claim` schema 不一致是否可达（见 I3）。

### 根因结构

1. **持久身份用了启动期局部量**：`st_dev` 是内核对挂载的编号，重启可重排；inode 才是目录级稳定量。
2. **身份判定与记录读取耦合**：`read_instance_set` 在解析记录时直接抛 `installation_changed`，导致“只读定位/停止”也被身份判定阻断，且无法表达“结构可读但身份待复核”的中间状态。
3. **同一个身份语义分散在 6+ 处比较**（F6），修一处不足以覆盖 `status/off/reload` 与陈旧实例清理。

## 方案设计

### 1. 身份契约（单一语义）

**同一安装 = 同一稳定卷标识 + 同一目录 inode + 同一规范化 project_root 字符串。** 持久化只写前两项；`project_root` 已由现有记录校验。

- macOS 稳定卷标识：APFS/HFS+ 卷 UUID（十六进制小写，规范化为 `8-4-4-4-12`）。
- inode：沿用 `_verify_directory` 已打开的目录 fd 的 `st_ino`。
- `st_dev` 降级为**仅启动期**用途：fd 与路径的交叉核对、同启动期内锁对象绑定；**任何持久记录不再保存 `device`**。
- Windows 保持现状（卷序列号 + file index 只活在运行期；记录 schema 3 不改）。

证据采集顺序（防路径换卷）：
1. 规范化并打开目标目录（现有 `O_NOFOLLOW|O_DIRECTORY` 与保护校验）。
2. `getattrlist(path, ATTR_VOL_INFO|ATTR_VOL_UUID)` 取卷 UUID（F4；不用 `fgetattrlist`，F5）。
3. `lstat(path)` 与 fd 的 `(st_dev, st_ino)` 必须一致，否则 `identity_evidence_changed`。
4. UUID 缺失/全零 → `volume_identity_unavailable`，不降级、不写记录。
5. `.runtime` 与项目根的 `st_dev` 在读取时须一致（同卷不变量，低成本补洞）。

### 2. 记录 schema 4（POSIX 三件套）

`INSTANCE_SCHEMA=2` 被多处当全局等式使用，不能直接改数。设计改为按记录/平台分派接受集：

- `POSIX_RECORD_SCHEMA = 4`（install / active / last_good_paths）
- 兼容读 `2`；Windows active 仍为 `3`，语义不变。
- `write_instance_record` 不得再硬编码单一 schema，须委托 `_valid_record` 的按记录分派（否则 Windows schema 3 会被拒写）。

identity 对象形状（严格 key 集，禁止额外字段）：

```json
"root_identity": {"kind":"macos_volume_uuid","uuid":"5ac2a76a-745b-493a-a82f-e1df050eae75","inode":271148775}
"locks": {
  "anchor": {"kind":"macos_volume_uuid","uuid":"5ac2a76a-…","inode":271344292},
  "legacy": {"kind":"macos_volume_uuid","uuid":"5ac2a76a-…","inode":271344295}
}
```

`last_good_paths` 无身份，但仍随集合升到 4，避免“半套版本”歧义。允许**逐记录混合** 2/4：迁移中途崩溃留下的 `install=4, active=2` 必须可读、可续迁移；不允许结构非法。

### 3. 身份判定状态机（读与判定分离）

`read_instance_set` 恢复职责单一：只做结构、保护、跨记录一致性校验，不再抛身份结论。新增判定函数返回显式裁决；安装身份判定仅用于 `on`/启动路径，身份不可得时 fail-closed。`status` / `off` 不做安装身份判定，不采集卷 UUID 与 inode，只依据进程活体、端口归属、锁活体给出结果：

| 裁决 | install 条件 | 动作 |
|---|---|---|
| `SAME` | schema 4，uuid+inode 均相等 | 放行 |
| `LEGACY_SAME_BOOT` | schema 2，inode 相等且 `device == 当前 st_dev` | 放行；持锁时就地升级到 4 |
| `LEGACY_OTHER_BOOT` | schema 2，inode 相等但 device 不等 | `installation_identity_unverified`；仅允许交互复核后重绑定 |
| `INODE_CHANGED` / `VOLUME_CHANGED` | schema 4 或 2，inode 不等 / uuid 不等 | `installation_changed`（真实变更，走完整重初始化） |
| `UNAVAILABLE` | UUID 取不到/为零、证据不一致 | `volume_identity_unavailable` / `identity_evidence_changed` |
| `INVALID` | 结构不合法 | `record_unavailable`（现有） |

active 锁身份两套语境：

| 语境 | 规则 |
|---|---|
| 活体校验（`status/off`） | 不做安装身份判定，不采集卷 UUID 与 inode；只依据进程活体、端口归属、锁活体给出结果 |
| 活体校验（`reload`） | 必须精确等于当前锁稳定身份；schema 2 另要求 `device == 当前 st_dev`，否则 `lock_identity_changed` |
| 陈旧实例判定（启动，已持双锁） | schema 4 不匹配 → `lock_identity_changed`（真实替换，不放行）；schema 2 且仅 device 不等、inode 相等 → 允许丢弃陈旧观测，但必须同时满足：双锁已持有、install 身份已被验证（schema 4）、记录进程证据为已退出/僵尸 |

**停止不判安装身份**：`off` 的定位读取只做结构校验，不做安装身份判定，不采集卷 UUID 与 inode，不报告安装身份告警；停止结果只依据进程活体、端口归属、锁活体。否则“卷变化/记录异常时无法停止服务”会放大故障。

### 4. 调用点接线（必须一次覆盖）

| 位置 | 改动 |
|---|---|
| `core/discovery.py` 身份/记录 | 新增卷 UUID 采集、稳定身份对象、判定函数；`read_instance_set` 去身份抛错；`_valid_record`/`write_instance_record` 按记录分派 schema 2/3/4；`initialize_installation` 写 schema 4 |
| `core/server.py:4515-4560, 4626-4650, 4714-4747, 5154-5200` | 启动时“结构读 → 身份判定 → 持锁迁移 → 锁身份判定 → 陈旧清理”；`_lock_identities`/`_instance_observation` 改用稳定身份 |
| `core/cli/authority.py:393-404, 993-1066, 1186-1206, 1267-1278, 1431-1451` | 状态机接入（`status/off` 不接入安装身份判定）；活体比较换稳定身份（`status/off` 除外，不采集卷 UUID 与 inode，只依据进程活体、端口归属、锁活体给出结果）；`locked_for_stop` 用结构读；新增 `rebaseline_interactively` |
| `core/cli/control.py:195-241, 458-492, 341-350` | `installation_state` 增加 `IDENTITY_UNVERIFIED`；`_prepare_initialization` 分支；`_valid_record` 稳定比较；新增安全 code 与错误文案 |
| `core/cli/windows_control.py` | 不改（schema 3 语义保持）；仅确认共享 `_valid_record`/写入口未回归 |

新增 code：`installation_identity_unverified`、`volume_identity_unavailable`、`identity_evidence_changed`；`installation_changed`、`lock_identity_changed` 语义不收窄。

### 5. 迁移与恢复

**自动升级（无需操作员）**：仅在服务启动、已持 anchor+legacy 锁、install 裁决为 `LEGACY_SAME_BOOT` 时执行。

1. 将三份记录复制到 `.runtime/backups/identity-v2-<UTC>/`（新建/复用受保护目录，0600、校验 ACL/单链接/属主；既有备份不移动、不覆盖）。
2. 顺序重写 `install.json` → `active.json`（若存在陈旧观测，先按第 3 节判定）→ `last_good_paths.json`；保留 `install_id`、`instance_nonce`、`ever_started`、`last_instance_nonce`、`project_root`、`initialization_source`。
3. 任一步失败：停止启动并报告实际写入状态；备份保留；不自动回滚、不删除记录。混合 2/4 状态下次可继续。
4. 只读操作（`status`）不触发迁移；不持锁不写。

**交互重绑定（LEGACY_OTHER_BOOT）**：`on` 在 `_prepare_initialization` 中识别新状态，要求同一 TTY，提示“记录来自另一启动/卷，目录 inode 未变”，要求显式确认后才写；条件：双锁持有、配置监听器已绑定（复用现有初始化租约机制）、`project_root` 与当前一致、inode 相等、UUID 可用。写 schema 4 并追加有界 `identity_history`（最多 8 条：时间、原因、旧 `{device,inode}`、新 `{uuid,inode}`、source），保留 `install_id`。inode 不等则不得重绑定，走完整重初始化（现有交互）。

**直接 server 启动**：不提供交互重绑定；身份未验证时拒绝并提示用 CLI（避免两个交互实现与无终端环境误判）。

**回退**：升级前备份可原样恢复三份记录（保持 0600），旧版本可读 schema 2；schema 4 记录旧版本会拒读，降级必须恢复备份，文档与发布说明须写明。

### 6. 入口 × 机制覆盖

| 入口 | install 身份 | active 锁身份 | 失败关闭 |
|---|---|---|---|
| `on` | 严格；未验证 → 交互重绑定 | 陈旧判定 | 不静默、不自动改记录 |
| 直接 server | 严格；拒绝 | 陈旧判定 | 提示 CLI 恢复 |
| `off` | **不做身份判定，不采集卷 UUID 与 inode**（结构+活体） | 锁活体，不比较持久身份 | 只依据进程活体、端口归属、锁活体给出结果 |
| `status` 运行中 | **不做身份判定，不采集卷 UUID 与 inode** | 锁活体，不比较持久身份 | 只依据进程活体、端口归属、锁活体给出结果，不报告安装身份告警 |
| `status` 已停 | **不做身份判定，不采集卷 UUID 与 inode** | 仅核对锁活体 | 只依据进程活体、端口归属、锁活体报告已停或活体证据异常，不报告安装身份告警 |
| `reload` | 严格（活体） | 活体锚锁 | 不重试盲发 |
| 初始化（无记录） | 不适用 | 不适用 | 现有交互不变 |

新旧版本共存与直启：

- 新代码 + 仍在运行的旧实例：记录是 schema 2 且 device 为当前启动期值，`status/off` 不做安装身份判定，不采集卷 UUID 与 inode，只依据进程活体、端口归属、锁活体给出结果；`reload` 与“已运行”判定的活体比较走 schema 2 等值分支，均可用；迁移只发生在服务启动持锁时，不会由只读操作触发。
- 旧代码 + schema 4 记录（含旧版直接 server 启动）：结构校验拒读（`record_unavailable`）。这是有意的降级阻断，必须用 §5 备份恢复后才能回退。

### 7. Windows 边界

不改 Windows 记录与启动路径：无 install.json、无持久卷身份比较，本类故障不成立。共享代码仅保证 schema 分派不回归。I3 的 schema 2/3 静态不一致按已确认裁决**单独立项跟进**，不在本方案内顺带修改（避免在无 Windows 原生验收条件下扩大改动面）。

### 方案推演

**具象走查（真实值）**

| 场景 | 记录 | 当前证据 | 裁决 | 结果 |
|---|---|---|---|---|
| 当前生产升级 | install schema2 `{16777233?→16777230, 271148775}`（现为 16777230） | uuid `5ac2…`、inode `271148775` | 升级前 device 相等 → `LEGACY_SAME_BOOT`；若 device 不等 → `LEGACY_OTHER_BOOT` | 前者自动升级；后者需一次交互 |
| 升级后再重启 | schema4 `{5ac2…,271148775}` | 同一 uuid+inode，device 任意 | `SAME` | 无操作 |
| 备份中的旧记录直接套到本启动 | schema2 `{16777233,271148775}` | device 16777230 | `LEGACY_OTHER_BOOT` | 拒绝静默启动，交互一次 |
| 目录换成另一卷同 inode | uuid 不同 | inode 同 | `VOLUME_CHANGED` | `installation_changed`，完整重初始化 |
| 同路径新目录 | inode 不同 | uuid 同 | `INODE_CHANGED` | `installation_changed` |
| 不洁重启留下 active | schema4 锁 `{5ac2,271344292/295}` | 当前锁同 uuid+inode，旧 pid 已退出/被复用 | 锁 `SAME` + 进程证据已退出 | 清理陈旧并启动 |
| 锁文件被替换 | schema4 inode 不同 | 双锁已持 | `lock_identity_changed` | 拒绝，不覆盖 |
| 卷 UUID 取不到 | 任意 | UUID 空 | `UNAVAILABLE` | 拒绝启动与写入 |

**时序语义**：升级发生在**服务进程持锁后、写 active 前**；因此“升级中途断电”最多留下 2/4 混合记录，不产生“schema 4 但无备份”的状态。`status` 在升级前只读，不会抢先改写。重启前后的边界只影响 device，不影响 uuid/inode。

**抽象推演**

- 论证链：前提 P1 卷 UUID 是落盘卷元数据；P2 inode 在同一文件系统内稳定；P3 记录同时保存 P1+P2 → 结论“跨重启同目录被判同安装”。隐含假设：UUID 不因擦除/恢复/迁移而保持与原卷相同。反例：用保留 UUID 的卷级克隆恢复到另一磁盘（APFS 克隆/迁移可能保留 UUID 与 inode），会被判为同安装——这是残余风险，威胁模型为误操作隔离而非对抗同用户，故接受并记录；不为此引入易被整体复制的 marker 身份。
- 结构不变量：①身份语义单点（新增/修改平台只需改一处采集+一处判定）；②读取与判定分离（解析器无策略，无环依赖）；③扩展点在平台 kind（新增平台只加一个采集器与一个校验分支）；④退化：schema 2 是 schema 4 的兼容特例，而非平行实现；⑤多入口覆盖见第 6 节矩阵，`status/off` 显式豁免安装身份判定与卷 UUID/inode 采集不构成缺口，因为结果另由进程活体、端口归属、锁活体证据链决定。

## 风险与权衡

### 方案比较

| 方案 | 可用性 | 安全/正确性 | 结论 |
|---|---|---|---|
| A：卷 UUID + inode，schema 4，读判分离，陈旧判定分级 | 重启透明；升级前已重启者需一次交互 | 保留真实变更检测；持久身份稳定；无静默降级 | **推荐** |
| B：保留 st_dev，跨启动时只比 inode（如用 boot session UUID 识别重启） | 较好 | 跨启动失去卷维度，移动/克隆更难识别；旧记录无 boot id，首次仍需交互 | 拒绝 |
| C：只用 inode（或目录内随机 marker） | 最好 | inode 跨卷可碰撞；marker 随目录复制，变更检测退化 | 拒绝为主身份，可作为无 UUID 时的备案（本环境用不到） |
| D：只修 install 身份，不修 active 锁身份 | 不洁重启仍会失败 | 留下已知第二故障 | 拒绝 |
| E：取消安装身份校验 | 无故障 | 丢失记录/账本跨目录复用的检测 | 拒绝 |

### 残余风险与取舍

- 卷级克隆保留 UUID+inode 时无法区分（见推演反例）；不引入可整体复制的 marker，避免“看起来更严、实际更弱”。
- UUID 采集是路径式调用，存在“校验后到取 UUID 前”的路径替换窗口；用 fd 的 dev/ino 交叉核对与前后保护重验压缩窗口，但不承诺对抗同用户/上层目录替换——与现有威胁模型一致。
- 重绑定是唯一的人机确认点；不可自动化，故无人值守环境下会保持停止（fail-closed），这是有意取舍。
- 迁移会改变记录 schema，旧版本不可读；降级需要备份恢复，发布说明必须显式写明。
- `status` 在不洁重启后不做安装身份判定，不采集卷 UUID 与 inode，只依据进程活体、端口归属、锁活体报告已停或活体证据异常，不报告安装身份告警，不自动清理；清理发生在启动。

### 已确认裁决（2026-11-22 用户拍板）

| 事项 | 裁决 |
|---|---|
| 升级前已跨重启的旧记录（device 变、inode 未变） | **交互重绑定一次**；不自动按 inode 接受 |
| 跨重启身份不符的恢复入口 | **复用 `on` 的初始化租约增加 `IDENTITY_UNVERIFIED` 分支**；不新增独立命令 |
| 记录版本 | **升 schema 4**；不采用“不加版本只加字段” |
| I3 的 Windows schema 2/3 静态不一致 | **单独立项跟进**，不并入本方案 |

上述裁决已落实到 §2（schema 4、判定状态机）、§5（自动升级与交互重绑定）、§6（入口矩阵）、§7（Windows 边界）。

剩余操作前提（非设计未决项）：真机验收需要一次用户批准的重启；本设计不请求、不执行。

## 验证方式

### 单元/注入测试

- 身份采集：注入假 UUID/空 UUID/证据不一致；断言裁决与 code。HFS+ 无真机样本，按 API 契约注入。
- schema：2/3/4 读取合法性、严格 key 集、混合 2/4 集合、非法字段拒绝；Windows schema 3 回归。
- 判定矩阵：第 3 节两张表逐格；重点 `LEGACY_SAME_BOOT` 与 `LEGACY_OTHER_BOOT` 的分界（device 等/不等、inode 等/不等）。
- 迁移：临时隔离项目写 schema 2 → 启动 → 断言 schema 4、`install_id` 保留、备份存在；在第 1/2/3 步注入写失败，断言无“半信任”放行且可续跑。
- 陈旧实例：schema 4 锁身份匹配 + pid 已退出 → 通过；pid 存活 → `process_still_active`；schema 4 锁身份不匹配 → `lock_identity_changed`。
- 状态/停止不判安装身份：构造 install 身份异常或卷 UUID/inode 采集不可用但进程活体、端口归属、锁活体均可验证的场景，断言 `status` 只报告活体结果、不报告安装身份告警，`off` 仍可完成，且两者均不调用卷 UUID 与 inode 采集；构造进程不可验证场景，断言拒绝。
- 重绑定：TTY 缺失拒绝；inode 不等拒绝；确认后保留 `install_id` 并写 `identity_history`（上限、字段、长度校验）。
- 运行入口：`python3 tests/run_unit_suite.py tests/test_mac_lifecycle_repairs.py tests/test_mac_config_control_recovery.py tests/test_windows_records.py`；隔离回归按 `tests/README-isolation.md` 走 `tests/run_isolated.sh`（需 `MP_TEST_*`），不得直接 `pytest tests/`。

### 隔离环境模拟

在 `tempfile` 或 `MP_TEST_*` 隔离开销内构造项目根 + `.runtime`，以注入的“当前卷 UUID/device”模拟重启前后两组证据，覆盖 `status/on/off/重启后启动/不洁重启` 全链路；不得写生产 `.runtime`，不得启动生产监听端口。

### 真机验收（需用户批准重启；本步不执行）

1. 升级前备份三份记录；升级后首次启动完成后确认 schema 4 + 备份目录内容。
2. 重启 #1：`status` 应只依据进程活体、端口归属、锁活体报告已停止，不判安装身份、不采集卷 UUID 与 inode、不报告安装身份告警；`on` 无需交互成功；确认无 `installation_changed`。
3. 重启 #2：重复，确认不是一次性巧合。
4. 不洁场景（可选，用户批准）：`kill -9` 服务进程后重启 → `on` 清理陈旧 active 并成功。
5. 降级演练：`off` → 恢复 schema 2 备份 → 旧版本 `status/on` 正常。
6. 记录观察点：`.runtime/install.json`、`active.json`、`.runtime/backups/…`、日志 `startup.listening` 与错误 code。

### 通过判据

连续两次重启无需人工干预可 `status/on`；真实目录替换/跨卷仍被拒绝；停止在身份异常时不被阻断；无静默记录改写；无新增凭据或路径泄露。
