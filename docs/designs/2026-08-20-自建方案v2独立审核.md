# 自建方案 v2 独立审核（[理想] 路径，只挑不重做）

审核基准：v2 全文 + 现网 settings/sessions 实证 + 补测实验（/tmp/hooktest2，claude 2.1.227 `-p`，2026-08-20）。

## 实测补验（v2 未实测的三项 MVP 前提，本次全过）

| 前提 | 结果 |
|---|---|
| hook 进程 env 含 `CLAUDE_CODE_SESSION_ID` | 成立，与 stdin JSON 的 session_id 一致（§6.1 快速路径基石坐实） |
| `UserPromptSubmit`→additionalContext | 生效（TOKEN-UPS 出现在最终答复） |
| `SessionStart` 在 `-p` 下触发且 additionalContext 生效 | 生效（source=startup） |

附带发现：hook 通道在 `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` 污染 env 下照常工作（四变量杀死官方通道、不影响自建）——v2 未写的鲁棒性优势。

## 硬伤（逻辑级，无实施级）

1. **§3"纯 -p 不写注册文件"以偏概全**：短命 `-p` 确实不写（本次复测确认）；但**长驻 stream-json `-p` 会写**，且 `kind:"interactive"` 与 Claudian 会话无法区分（现存 54926/55390 即是，注册文件 kind 均为 interactive）。→ registry 补登记的真实适用面只剩"短命 -p"（其本不适合收消息），**registry 必要性需重论证**；kind 字段不可作形态判据。
2. **T4 半句不成立**：触发条件列"跨非 CC 上游（glm/kimi）互通"，但本方案 hook 在 CC 层，codex 等非 CC 会话不可达——该需求触发时本备案同样无解，应删此半句或标注"另立方案"。

## 遗漏清单（按影响排序）

1. **Claude 侧触发机制整体缺失**：Claude 怎么知道 `msg` 存在、何时用？被动回复有 reply_hint，但主动场景（用户说"告诉 X …"）无入口——CLAUDE.md 注入或 mini skill，MVP 必须含，v2 未着一字。
2. **可达性矩阵缺失**：hook 只能搭活动便车，**完全空闲（无人、无 turn）的 session 结构性不可达，Stop 也救不了**（最后的 Stop 已触发过，不会再有）——官方 socket 可推、自建不能，这是"自建=官方降级替代"的根本差距，埋在风险 6 里弱化了。应显式成表（忙时/人在线/空闲 × 官方/自建），并让"需要空闲唤醒"成为不启用自建的理由。
3. **T5 与项目级 hook 的约束矛盾**：hook 装 vault 项目级 → headless worker 必须在 vault cwd 启动才有投递/补登记，v2 未写该约束（或提供 user 级安装选项）。
4. **MVP 内部矛盾**：§7 的 `--to-human` 属 MVP CLI，但 systemMessage 可见性未实测且排二期——MVP 里 to-human 消息可能无人可见。应砍出 MVP 或实测提前。
5. **§8 现状盘点漏 `route_guard.sh`**：现网实为 4 脚本 5 条目（PreToolUse×3 + SessionStart×2）。install 靠 command 子串判归属不致破坏，但枚举错误防 implementer 拿它当白名单。
6. **Stop 二期理由失实**："需环路守卫实测"——`stop_hook_active` 已实测（§4 第三行）；真实理由是增量小（turn 间隙已被 PostToolUse 覆盖）。理由要改，结论可维持。

## 优化建议

**值得改**：①补"Claude 侧入口"设计（遗漏 1）；②加可达性矩阵 + 明确**启用自建后统一走自建**（自建覆盖 ⊇ 官方激活子集；官方 SendMessage 发向未激活 session 的行为未验，有静默丢风险，"由人选一条"太弱）；③存活校验加进程身份（`ps -p <pid> -o comm=`=claude），防 pid 复用误判；④§4 实测表补 UserPromptSubmit/SessionStart 两行（本次代测可引）；⑤修硬伤 1/2 的表述并重写 registry 一节。
**可选**：gbcache `check` 退出码分级联动 T1 判定（restore 后仍不绑 → 输出"建议启用自建备案"）；升级后 SOP 合并（gbcache S2 + hook 哨兵回归一张清单）；reply_hint 附 sessionId（name 可改名/重名）；快速路径不 drain stdin 时 CC 对 EPIPE 的容忍性待实测；明示 at-least-once 语义（cur/ 残留重投 + archive 前崩溃 → 重复消费，接收方按 msg id 幂等）；T1"连续告警"定义次数（如 ≥2 次）。

## 总体结论

核心路线（hook 投递 + maildir + CLI 发送）成立且实测地基比 v2 自述更稳。当前**未达**"implementer 拿着能落地"完备度——差四件事：Claude 侧触发机制、可达性矩阵与双通道策略、T5 worker cwd 约束、registry 必要性重论证。补齐后即可开工。MVP 其余切分（Stop 缓行、审计先行）判断合理。
