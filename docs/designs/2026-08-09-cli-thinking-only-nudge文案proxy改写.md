# CLI thinking_only_retry nudge 文案的 proxy 层改写方案

## 背景与问题

根因调研（vault 顶层 docs/designs/2026-08-09-claudian空消息与thinking-only根因调研.md）确认：kimi-k3 thinking-only 响应 → claude CLI 2.1.197 内置 `thinking_only_retry` 注入 user 消息 `[Your previous response had no visible output. Please continue and produce a user-visible response.]`（isMeta，94 字符，硬编码孤立字符串）→ kimi 误读为"用户发空消息"进入退化循环。用户不想 hex 改 CLI 二进制（签名/升级覆盖风险），要求在 model_proxy 层拦截改写该文案。本文评估可行性并给出改动清单。

## 可行性结论

**技术可行，改动小、fail-open、无副作用；但射程有限——只治"nudge 误读"（pattern A），不治占投诉大头的"tool_result 轮误读"（pattern B）。建议做，但预期收益要设对。**

### 射程边界（关键诚实声明）

对 3 个受影响 session 的投诉重新归因：

| session | 投诉数 | nudge 注入数 | nudge 位置 vs 投诉位置 | 主 pattern |
|---|---|---|---|---|
| 4eb3be5f | 24 | 5 | nudge 与投诉交织 | A（nudge 循环） |
| 2896beec | 30 | 2 | **nudge 在 line 3454，全部 30 次投诉在 line 1308-3375，均早于 nudge** | B |
| 1a09afa5 | 51 | **0** | 无 nudge | B |

pattern B：kimi 把 tool_result-only 的 user 轮（Agent 结果、Bash 输出、TaskOutput 超时轮询）误读为"用户发空消息"。疑似机制：网关在 anthropic tool_result user 消息转 kimi 格式时，在工具结果后补了一个空 user 轮（kimi 模板要求生成前末轮为 user），kimi 看到的字面上就是空用户消息——这解释了"(no content)"占位符的一致性和投诉前导的多样性。**网关黑盒，无法从本侧证实，需鉴别实验（见验证 E2）。**

本方案只改写 nudge 文案，对 pattern B 无直接作用。间接收益：消除 pattern A 的"空消息叙事"bootstrap 后，叙事先验弱化，pattern B 抱怨频率可能下降（假设，需观察验证）。

## 方案设计（推荐：做）

### 链路确认（已实证）

- CLI 注入的 nudge 在 transcript 中是 `role:user`、`content` 为纯字符串、`isMeta:true`（4eb3be5f:1131 原始记录核实）。isMeta 只是 UI 隐藏标记，**会进 API 请求**——kimi 在 nudge 后的 thinking 明确回应了 nudge 内容（"前面陷入了'只说不做'的循环"，4eb3be5f:1134）。
- 因此 proxy 在转发请求时能在 `body_json["messages"]` 里看到它，形态为普通 user 消息（string content；防御性地兼容 text block 形态）。

### 改动清单（2 处，均在 tools/model_proxy/core/server.py）

**改动 1：新增模块级函数**（建议放在 `extract_session_key`（658 行）之后、`detect_source`（684 行）之前）：

```python
# 已知 SDK 注入文案改写表（docs/designs/2026-08-09-cli-thinking-only-nudge文案proxy改写.md）。
# 键：claude CLI thinking_only_retry 注入的 nudge 原文（2.1.197 硬编码孤立字符串，
# CLI 升级若改文案则静默失配——fail-open 原样透传，无崩溃风险）。
_NUDGE_TEXT_ORIG = ("[Your previous response had no visible output. "
                    "Please continue and produce a user-visible response.]")
_NUDGE_TEXT_REWRITTEN = (
    "[Harness auto-retry notice — generated by the client runtime, NOT by the user. "
    "The user did not send an empty message. "
    "Your previous turn contained only internal reasoning with no visible output, "
    "so no tool was executed. Skip any apology or meta-commentary: "
    "immediately issue the pending tool call, or produce a normal visible reply.]"
)

def _rewrite_known_injected_texts(body: dict) -> bool:
    """精确改写已知 SDK 注入文案（user 消息的 string / text block 两种形态）。

    返回是否发生改写（调用方据此重序列化 raw_body）。精确匹配（strip 后全等），
    不做子串替换；不匹配一律原样保留（fail-open）。
    """
    messages = body.get("messages") if isinstance(body, dict) else None
    if not isinstance(messages, list):
        return False
    dirty = False
    for msg in messages:
        if not isinstance(msg, dict) or msg.get("role") != "user":
            continue
        content = msg.get("content")
        if isinstance(content, str):
            if content.strip() == _NUDGE_TEXT_ORIG:
                msg["content"] = _NUDGE_TEXT_REWRITTEN
                dirty = True
        elif isinstance(content, list):
            for blk in content:
                if (isinstance(blk, dict) and blk.get("type") == "text"
                        and isinstance(blk.get("text"), str)
                        and blk["text"].strip() == _NUDGE_TEXT_ORIG):
                    blk["text"] = _NUDGE_TEXT_REWRITTEN
                    dirty = True
    if dirty:
        log.info("nudge text rewritten (thinking_only_retry)")
    return dirty
```

**改动 2：`_forward` 步骤 3（body 解析）之后插入调用**（当前 1168 行 `body_json = None` 之后、1169 行 `request_model = ...` 之前）：

```python
        # 3.5 已知注入文案改写：CLI nudge 等，见函数注释。改写后重序列化 raw_body，
        # 使 PASSTHROUGH 分支（send_body = raw_body，1436 行）在无其他 body 变更时
        # 也能带出改写；re-dump 与既有 model 改写路径（1439 行）同款操作，安全。
        if isinstance(body_json, dict):
            if _rewrite_known_injected_texts(body_json):
                raw_body = json.dumps(body_json, ensure_ascii=False).encode("utf-8")
```

为什么放这里而不是 PASSTHROUGH 分支内：body_json 是所有四种转发模式（passthrough/to-chat/to-responses/反向）的共同输入，单点插入全覆盖；重赋值 raw_body 后，passthrough 的 `send_body = raw_body`（1436 行）自然带出改写，mode 分支零改动。

**改动 3：测试**（新增 tools/model_proxy/tests/test_nudge_rewrite.py）：
- string 形态精确命中改写；text block 形态命中改写
- 非 user role / 相似但不全等文案 / 空 messages / messages 非 list → 原样返回 False
- 改写后 `_forward` 重序列化（可用现有 server 测试框架，或直接单测函数 + 人工核对插入点）

验证命令：`cd tools/model_proxy && python3 -m pytest tests/ -x -q`（现有 478 测试须保持全绿）。

### 文案设计原则（为何这样写）

1. **明确归因**：`generated by the client runtime, NOT by the user` + `The user did not send an empty message`——直接否定误读点。
2. **解释工具为何没执行**：`no tool was executed`——消解"Bash 没执行成"的困惑叙事。
3. **命令式恢复**：`immediately issue the pending tool call, or produce a normal visible reply`——保留 nudge 机制的功能意图（对 claude 语义等价，行为不变）。
4. **抑制叙事**：`Skip any apology or meta-commentary`——打断"道歉→分析故障→再 thinking-only"的自我强化。
5. 保持英文、方括号 harness 消息惯例；避免 "(no content)"/"empty message" 以外的触发词（保留一处否定式引用是有意的，直接对冲先验）。

## 影响面

- **生效范围**：所有经 proxy 的 anthropic source 请求（claude route 同为 anthropic passthrough，一并生效）。改写对 claude 语义等价，行为不变；nation route 是受益对象。responses source（codex）body 无 messages 字段，helper 自然 no-op。
- **误伤风险**：仅当真实用户逐字粘贴这 94 字符原文时会被替换——可接受，已在代码注释声明。精确全等匹配，不做子串/模糊匹配。
- **与 proxy 其他职责的关系**：raw_intent 的 reasoning decode（1257 行）不读消息文本，不受影响；内建命令门控（1192-1200 行）的 parse_route_command 只认 `$` 前缀，nudge 文案命中不了，改写提前执行亦无影响；budget/failover/流式路径零接触。
- **性能**：每请求 O(messages) 次字符串比较，可忽略。
- **可观测性**：每次改写 log.info 一条；若 CLI 升级改了文案导致失配，症状复发时 grep 日志无 "nudge text rewritten" 即可定位。
- **与会话历史的关系**：CLI 每次请求都重放全量历史，历史中的旧 nudge 每次都会被重新改写——存量已污染 session 同样受益，无需 /clear。

## 层次二评估（proxy 自检测 thinking-only + 重试）：不推荐

- 流式响应边收边转（`_write_streaming_response`/`_write_translated_stream`），判定 thinking-only 需看到 message_stop——要干预就得**整响应缓冲**，nation 全量请求的首 token 延迟退化为整段生成时长（实测 5-150s），UX 回退太大。
- 即便检测到，重试 body 不变，kimi 再出 thinking-only 的概率不低；且 CLI 已有 nudge 机制做同样的事——层次二是高成本重复造轮子。
- 对比：改文案以约 1% 的复杂度拿到该链路 80% 的可得收益（nudge 恢复率提升 + 叙事消除）。首次 thinking-only 的代价（~80 output tokens + 一次 nudge 往返）本就可忽略。

## 与根因的对治关系

| 环节 | 本方案是否治 |
|---|---|
| kimi 首次 thinking-only（模型/网关行为） | 不治（不可控，代价可忽略） |
| CLI nudge 注入（上游特性） | 不治机制本身，改其文案使 kimi 正读 |
| kimi 误读 nudge → "空消息"叙事循环（pattern A） | **治，本方案核心** |
| kimi 误读 tool_result-only 轮（pattern B，占投诉大头） | **不治**——疑似网关在工具结果后补空 user 轮，proxy 改 nudge 鞭长莫及；改写 tool_result 内容风险高，明确不推荐 |
| 根解 | 仍是主工作 session 切 claude route（前份调研报告建议 1） |

kimi 改文案后不再误读的概率：无法事前定量。依据是误读三要素中（nudge 归因模糊 / 自身不可见轮在历史 / "(no content)" 训练先验），新文案显式消除第一个、文字对冲第三个；第二个仍在。故残留风险存在，用验证 E1 观察收敛情况。

## 验证方式

- **E0（单元）**：pytest 全绿 + 新测试覆盖两形态/失配/异常输入。
- **E1（实机，验证 pattern A 收敛）**：改后重启 proxy（`model_proxy_cli.sh` restart），在 nation session 正常工作；症状曾现后：① proxy log grep "nudge text rewritten" 确认拦截生效；② 对应 transcript 中 nudge 后 kimi 的 thinking 不再把 nudge 称为"空消息/(no content)"（注意 transcript 记录的是 CLI 原始文案，验证看 kimi 的回应文本）；③ 投诉频率对比基线（4eb3be5f 24 次/2 天、2896beec 30 次、1a09afa5 51 次）。
- **E2（鉴别 pattern B 机制，curl 实验，强烈建议做）**：构造最小 anthropic 请求直发 nation route：user 文本 → assistant tool_use → user tool_result，问 kimi"最后一条用户消息的内容是什么"。若 kimi 答"空消息"之类 → 网关补空 user 轮假设坐实，pattern B 确凿在网关侧，拿实验记录向网关/kimi 提供方报障；若正常 → pattern B 与长上下文/历史复杂度相关，另行归因。
- **E3（失配监控）**：CLI 升级后若症状复发，先 grep proxy log 确认 nudge 改写是否还在生效。
