# CLI thinking_only_retry nudge 文案的 proxy 层改写方案

## 背景与问题

根因调研（vault 顶层 docs/designs/2026-08-09-claudian空消息与thinking-only根因调研.md）确认：kimi-k3 thinking-only 响应 → claude CLI 2.1.197 内置 `thinking_only_retry` 注入 user 消息 `[Your previous response had no visible output. Please continue and produce a user-visible response.]`（isMeta，94 字符，硬编码孤立字符串）→ kimi 误读为"用户发空消息"进入退化循环。用户不想 hex 改 CLI 二进制（签名/升级覆盖风险），要求在 model_proxy 层拦截改写该文案。本文评估可行性并给出改动清单。

## 可行性结论

**技术可行，改动小、fail-open、无副作用；但射程有限——只治"nudge 误读"（pattern A），不治占投诉大头的"tool_result 轮误读"（pattern B）。建议做，但预期收益要设对。**

### 射程边界（关键诚实声明）

对 3 个受影响 session 的投诉重新归因：

| session | 投诉数 | nudge 注入数 | nudge 位置 vs 投诉位置 | 主 pattern |
|---|---|---|---|---|
| 4eb3be5f | 24 | 5 | nudge 与投诉交织 | A（nudge 循环） |
| 2896beec | 30 | 2 | **nudge 在 line 3454，全部 30 次投诉在 line 1308-3375，均早于 nudge** | B |
| 1a09afa5 | 51 | **0** | 无 nudge | B |

pattern B：kimi 把 tool_result-only 的 user 轮（Agent 结果、Bash 输出、TaskOutput 超时轮询）误读为"用户发空消息"。疑似机制：网关在 anthropic tool_result user 消息转 kimi 格式时，在工具结果后补了一个空 user 轮（kimi 模板要求生成前末轮为 user），kimi 看到的字面上就是空用户消息——这解释了"(no content)"占位符的一致性和投诉前导的多样性。**网关黑盒，无法从本侧证实，需鉴别实验（见验证 E2）。**

本方案只改写 nudge 文案，对 pattern B 无直接作用。间接收益：消除 pattern A 的"空消息叙事"bootstrap 后，叙事先验弱化，pattern B 抱怨频率可能下降（假设，需观察验证）。

## 方案设计（推荐：做）

### 链路确认（已实证）

- CLI 注入的 nudge 在 transcript 中是 `role:user`、`content` 为纯字符串、`isMeta:true`（4eb3be5f:1131 原始记录核实）。isMeta 只是 UI 隐藏标记，**会进 API 请求**——kimi 在 nudge 后的 thinking 明确回应了 nudge 内容（"前面陷入了'只说不做'的循环"，4eb3be5f:1134）。
- 因此 proxy 在转发请求时能在 `body_json["messages"]` 里看到它，形态为普通 user 消息（string content；防御性地兼容 text block 形态）。

### 改动清单（2 处，均在 tools/model_proxy/core/server.py）

**改动 1：新增模块级函数**（建议放在 `extract_session_key`（658 行）之后、`detect_source`（684 行）之前）：

```python
# 已知 SDK 注入文案改写表（docs/designs/2026-08-09-cli-thinking-only-nudge文案proxy改写.md）。
# 键：claude CLI thinking_only_retry 注入的 nudge 原文（2.1.197 硬编码孤立字符串，
# CLI 升级若改文案则静默失配——fail-open 原样透传，无崩溃风险；失配主动核对方式见
# 验证方式 E3）。
_NUDGE_TEXT_ORIG = ("[Your previous response had no visible output. "
                    "Please continue and produce a user-visible response.]")
_NUDGE_TEXT_REWRITTEN = (
    "[Harness auto-retry notice — generated by the client runtime, NOT by the user. "
    "The user did not send an empty message. "
    "Your previous turn contained only internal reasoning with no visible output, "
    "so nothing was executed. Skip any apology or meta-commentary: "
    "if you intended to call a tool, emit the tool call now; "
    "otherwise produce your visible reply now.]"
)

def _rewrite_known_injected_texts(body: dict) -> bool:
    """精确改写已知 SDK 注入文案（user 消息的 string / text block 两种形态）。

    纯函数，返回是否发生改写（调用方据此重序列化 raw_body + 置 _acc 观测字段）。
    精确匹配（strip 后全等），不做子串替换；不匹配一律原样保留（fail-open）。
    """
    messages = body.get("messages") if isinstance(body, dict) else None
    if not isinstance(messages, list):
        return False
    dirty = False
    for msg in messages:
        if not isinstance(msg, dict) or msg.get("role") != "user":
            continue
        content = msg.get("content")
        if isinstance(content, str):
            if content.strip() == _NUDGE_TEXT_ORIG:
                msg["content"] = _NUDGE_TEXT_REWRITTEN
                dirty = True
        elif isinstance(content, list):
            for blk in content:
                if (isinstance(blk, dict) and blk.get("type") == "text"
                        and isinstance(blk.get("text"), str)
                        and blk["text"].strip() == _NUDGE_TEXT_ORIG):
                    blk["text"] = _NUDGE_TEXT_REWRITTEN
                    dirty = True
    return dirty
```

### 复用评估（v2 新增）：能否复用内建命令（$route 门控）的"规则层能力"？

**结论：无可复用的规则层——内建命令本身就是一段硬编码 if + 命令执行封装，且与 nudge 改写语义正交；不抽统一规则层，保持两个独立小 if。**

内建命令设施的现状形态（精读 server.py:1184-1200 / 1801-1856 + commands.py 后如实记录）：

- 门控点是一段硬编码 if（server.py:1192-1200）：source==anthropic + session_key 非空 + body_json 含 messages list + strategy 匹配 → `extract_last_user_message_content` → `parse_route_command`（$ 前缀、单行、≤2 token、fail-open）→ 命中则 `_handle_builtin_command` 消费请求、自造响应、**早返回不转发**。
- 配套抽象（commands.py 的 `CommandContext/CommandResult/COMMAND_HANDLERS` 分发表）是**命令执行**封装，语义为"拦截-改道-本地应答"；分发表注释自述为"未来扩展命令预留"。
- 周边设施：`SessionOverridesSidecar`（route override 热重载存储）、`extract_session_key`（session 哈希分派用）——均为 route 命令专用，nudge 改写无状态、用不上。

两条规则的性质差异，决定它们不适合同一抽象：

| 维度 | $ 门控 | nudge 改写 |
|---|---|---|
| 控制流 | intercept-and-respond（消费请求、早返回） | mutate-and-continue（改完放行、照常转发） |
| 匹配范围 | 只取**最后一条** user 消息（"用户这轮打的话"，last_text_block 还有"只取末个 text 块"的特殊口径） | 扫**全量历史** user 消息（CLI 每次重放全量历史，旧 nudge 每条都要改） |
| 匹配方式 | 结构解析（前缀/单行/token 数） | 整串全等 |
| 前置依赖 | 需 session_key + strategy 就绪 | 只需 body 已解析 |

`COMMAND_HANDLERS` 挂不进"改完放行"的动作（它的 action 语义是本地应答）；`extract_last_user_message_content`/`last_text_block` 的口径与 nudge 需要的全量扫描相反。强套统一抽象（如 `rules: list[(match, action)]`、action 分 intercept/rewrite）的代价：两规则的 match 输入不同，要么各自为政（抽象名存实亡），要么构造大而全的 RequestContext（为 2 条规则发明框架）；读代码的人还要在 rules 定义与循环骨架间跳读。**YAGNI：2 条正交规则，抽层收益≈0，反而更绕；第 3 条同类规则出现时（有 3 个样本才知道抽象该长什么样）再抽不迟。**

v2 仅做的对齐性微调（非抽层）：插入点移到命令门控前，两处前置处理在代码里相邻、注释分区风格一致（"---- ... ----"横幅），后来人一眼看到"_forward 开头有两个前置处理"。

**演进记录**：v1（2026-08-09 初版）插入点定在 1168 行 body 解析后；v2（同日，复用评估后）微调到 1192 行命令门控前，新增复用评估结论；v3（同日，独立 architect-max [理想] 审查后）采纳 9 条修订：文案定指改条件式（S1）、调用处加 source=="anthropic" 门控（S2）、"对 claude 行为不变"措辞降级并记录不后移插点的取舍（S3）、观测从 helper 内 log.info 改为 ACCESS `nudge_rewritten` 字段（S4，顺带解决 O5 语义）、E3 改为主动 strings 核对（S4）、"删除 nudge"排除理由留痕（S5）、测试计划加 _forward 全程集成测试并修正为 unittest/612（M1/M2）、"94 字符"改 100（O1）、否定式引用预案（O2）、re-dump 副作用补记（O3）、无配置开关决策留痕（O4）。驳回 0 条。

### 文案设计原则（为何这样写）

1. **明确归因**：`generated by the client runtime, NOT by the user` + `The user did not send an empty message`——直接否定误读点。
2. **解释工具为何没执行**：`nothing was executed`——消解"Bash 没执行成"的困惑叙事。
3. **条件式恢复（v3 修订）**：`if you intended to call a tool, emit the tool call now; otherwise produce your visible reply now`——v1 的 "immediately issue the pending tool call" 是定指，隐含"存在待发工具调用"的预设；但 nudge 触发条件是"无可见输出"（无任何 text block），模型本想输出纯文本（无 pending tool call）时同样触发，定指成悬空指代，有诱发幻觉工具调用的风险。改为条件双分支后两分支均保持祈使力度，kimi 对简单条件句的遵循能力足够，不损恢复力。
4. **抑制叙事**：`Skip any apology or meta-commentary`——打断"道歉→分析故障→再 thinking-only"的自我强化。
5. 保持英文、方括号 harness 消息惯例。
6. **否定式引用的双刃预案（v3 新增）**：`The user did not send an empty message` 含 "empty message"，否定句注意力反转是已知现象，kimi 可能抓住该词反而强化叙事。E1 观察期若误读未收敛，去掉否定句改纯肯定式：`The most recent user-role turn is this automated notice itself; no new input from the human.`——作为既定预案留痕，届时直接替换。

## 影响面

- **生效范围（v3 修订）**：source=="anthropic" 的请求（claude route 与 nation route 同为 anthropic passthrough，一并生效；chat/responses source 被调用处门控排除）。对 claude 的表述从"语义等价、行为不变"降级为：**语义更强的同向指令**（新文案多了"Skip any apology""立即产出"两条强指令），行为预期同向但非严格不变；E1 观察期同时留意 claude route。若要求 claude 零影响须把插点后移到 route 选定之后——那会失去单点覆盖（各 mode 分支分别处理 + passthrough raw_body 路径复杂化），而 nudge 本就罕见、指令语义同向、下行风险极低，**取舍：不后移**，留痕备查。
- **误伤风险**：仅当真实用户逐字粘贴这 100 字符原文（v1 误写 94）时会被替换——可接受。精确全等匹配，不做子串/模糊匹配。
- **re-dump 副作用（v3 补记）**：命中改写后全量 re-dump 使 passthrough 不再字节级一致（json.loads 合并重复 key、规范化数字/空白），与既有 1439/1445/1453 三条 re-dump 路径同款，对正常请求无实际影响。
- **与 proxy 其他职责的关系**：raw_intent 的 reasoning decode（1257 行）不读消息文本，不受影响；内建命令门控的 parse_route_command 只认 `$` 前缀，nudge 文案命中不了，改写提前执行亦无影响；budget/failover/流式路径零接触。
- **性能**：每请求 O(messages) 次字符串比较，可忽略。
- **可观测性（v3 修订）**：ACCESS 日志新增 `nudge_rewritten` 字段（含 session/route 关联键；语义为"入站 body 命中改写"，$route 等未转发请求命中时也会置位，属预期）。失配的主动核对见验证方式 E3。
- **无配置开关（v3 留痕）**：有意不加——单条硬编码规则加开关是伪灵活；未来出现第二条同类规则时连同规则层一起重新评估（见"复用评估"节）。
- **与会话历史的关系**：CLI 每次请求都重放全量历史，历史中的旧 nudge 每次都会被重新改写——存量已污染 session 同样受益，无需 /clear。

### 已排除的替代方案（v3 补记留痕）

- **直接删除 nudge 消息**：排除。① 删除后历史出现相邻 assistant 消息（nudge 前一条恰是 thinking-only 的 assistant 轮；后续请求的历史为 …assistant(thinking-only), assistant（新响应）…），真 anthropic 上游（claude route）会因 roles 不交替直接 400；② 删除使重试请求体与上一轮几乎相同，模型无新信息，更可能重复 thinking-only——丢失 CLI nudge 机制的功能意图。
- **改写 tool_result 内容治 pattern B**：排除，见"与根因的对治关系"表。

## 层次二评估（proxy 自检测 thinking-only + 重试）：不推荐

- 流式响应边收边转（`_write_streaming_response`/`_write_translated_stream`），判定 thinking-only 需看到 message_stop——要干预就得**整响应缓冲**，nation 全量请求的首 token 延迟退化为整段生成时长（实测 5-150s），UX 回退太大。
- 即便检测到，重试 body 不变，kimi 再出 thinking-only 的概率不低；且 CLI 已有 nudge 机制做同样的事——层次二是高成本重复造轮子。
- 对比：改文案以约 1% 的复杂度拿到该链路 80% 的可得收益（nudge 恢复率提升 + 叙事消除）。首次 thinking-only 的代价（~80 output tokens + 一次 nudge 往返）本就可忽略。

## 与根因的对治关系

| 环节 | 本方案是否治 |
|---|---|
| kimi 首次 thinking-only（模型/网关行为） | 不治（不可控，代价可忽略） |
| CLI nudge 注入（上游特性） | 不治机制本身，改其文案使 kimi 正读 |
| kimi 误读 nudge → "空消息"叙事循环（pattern A） | **治，本方案核心** |
| kimi 误读 tool_result-only 轮（pattern B，占投诉大头） | **不治**——E2 实验已证伪"网关系统性补空 user 轮"，触发条件未明（见实验实录）；改写 tool_result 内容风险高，明确不推荐 |
| 根解 | 仍是主工作 session 切 claude route（前份调研报告建议 1） |

kimi 改文案后不再误读的概率：无法事前定量。依据是误读三要素中（nudge 归因模糊 / 自身不可见轮在历史 / "(no content)" 训练先验），新文案显式消除第一个、文字对冲第三个；第二个仍在。故残留风险存在，用验证 E1 观察收敛情况。

| C | 直连网关→claude-opus-5（格式对照） | 同 A body | 未执行成：429（AppId 0956 用量上限）；格式有效性由 A/B 正确回答旁证 |
| D | proxy→nation | 6 轮 tool_use/tool_result 循环 | 阴性 |
| D2 | proxy→nation | tool_result 为 TaskOutput 超时轮询（1a09afa5 投诉前导同款载荷） | 阴性：正确处理"任务仍在运行" |
| F | proxy→nation | tool_result content 双 text block（Agent 结果真实形态） | 阴性 |
| G2 | proxy→nation | 重放 2896beec 真实历史（重构 535 条消息、1.15MB、279K input tokens，截至首个投诉点 line 1305），5 次独立采样 | **5/5 阴性**，每次均正确总结 architect 评估（生产上 kimi 却声称"还没派出 agent/用户发空消息"） |

**附带发现（G 首次 400 报文）**：网关错误原文 "an assistant message with 'tool_calls' must be followed by tool messages responding to each 'tool_call_id'... Bash:0"——证明 nation 网关内部把 anthropic 格式**再转换为 OpenAI chat 格式**（tool_calls/tool messages 措辞），且把工具 id 改名为 `{name}:{n}`。即 proxy 的 anthropic 透传只到网关，网关自己对 kimi 做二次协议转换。此事实与 pattern B 后续归因直接相关。

G2 与生产的已知偏差：无 Claudian system prompt；工具 schema 为 dummy；非流式；9 个悬空 tool_use 注入了合成的 CC 标准中断文案（这些 tool_use 的结果因 transcript 分支结构未入链）。

### 实验结论

1. **"网关在 tool_result 后系统性补空 user 轮"假设证伪**：若系统性存在，535 条消息中几十处 tool_result 必触发，不可能 5/5 阴性。
2. **Pattern B 最小复现失败，触发条件未明**。残余可能：低概率采样误读（5 次阴性不排除个位数百分比发生率）；依赖未复现变量（system prompt、流式、当日网关/模型版本——投诉集中 8/7-8/9，不排除上游当时版本退化、现已变化）。
3. 单次阴性不能排除；但"最小三元组→多轮→超时轮询→多块结果→真实历史×5"全链阴性，说明 pattern B 不是确定性协议 artifact，而是低概率/条件性模型行为。

### Pattern B 下一步建议

- **症状嗅探落证**（可选、默认关闭的 proxy 小功能）：流式回传累积 text delta，流末匹配 "空消息/(no content)" 关键词，命中则把该请求 body + 响应文本落盘 debug 目录。把下一次实机发生变成硬证据（拿到网关真实入参），届时可持请求体向网关/kimi 方报障。复杂度中等，与 nudge 改写相互独立。
- nudge 改写（pattern A）按本方案照常落地，不受实验结果影响。
- 若切 claude route 后症状消失，pattern B 仅以嗅探监控观察即可，不再深挖。

## 验证方式

- **E0（单元+集成）**：`python3 -m unittest discover -s tests` 全绿（基线 612）+ 新测试覆盖两形态/失配/异常输入/_forward 全程集成（见改动 3）。
- **E1（实机，验证 pattern A 收敛）**：改后重启 proxy（`model_proxy_cli.sh` restart），在 nation session 正常工作；症状曾现后：① ACCESS 日志 grep `nudge_rewritten=1` 确认拦截生效；② 对应 transcript 中 nudge 后 kimi 的 thinking 不再把 nudge 称为"空消息/(no content)"（注意 transcript 记录的是 CLI 原始文案，验证看 kimi 的回应文本）；③ 投诉频率对比基线（4eb3be5f 24 次/2 天、2896beec 30 次、1a09afa5 51 次）；④ 同时留意 claude route 有无异常（影响面节的取舍项）。
- **E2（鉴别 pattern B 机制）**：已执行，见上方实录——假设证伪/未复现，结论以实录为准。
- **E3（失配监控，v3 修订为主动核对）**：CLI 升级后主动跑 `strings $(readlink -f $(which claude)) | grep -F "previous response had no visible output"`——无输出即原文案已变，需更新 `_NUDGE_TEXT_ORIG`；有输出则被动依赖 ACCESS 日志的 `nudge_rewritten` 字段即可。
