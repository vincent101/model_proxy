# 背景与问题

在跨协议终态化与首帧预读已上线的前提下，全面审计异常逃逸、静默成功、流边界、状态污染、配置与观测盲区；当前 `756 passed` 不能覆盖生产中已出现的“HTTP 200 已提交、流无终态且无错误记录”。

审计基线：`HEAD=a3a162ccf2a8a0ed5b76278c37d20472b054c467`，工作区审计前后均干净。范围：`core/server.py`、`core/translate.py`、`_config_ops.py`、`_format_ops.py`、`core/commands.py`、启动脚本、测试、`.model_proxy.log`。静态枚举 89 个 `try`（server 62、translate 7、config 10、format 10），并用 `/tmp`/内联最小探针验证关键假设。

# 方案设计

## 1. 结论与风险矩阵

| 严重度 | 数量 | 定义 | 主要后果 |
|---|---:|---|---|
| 阻断 | 2 | 已有活体或可稳定复现，破坏 fail-fast/终态不变量 | 已提交流静默断裂；非流 200 坏响应静默成功 |
| 高 | 8 | 可导致请求线程逃逸、长时间占用、内存/状态越界或错误配置生效 | 500/断流、最长 3 小时等待、跨 attempt 污染 |
| 中 | 8 | 边界语义、观测或测试覆盖存在明确缺口 | 误判、难定位、回归假绿 |
| 低 | 4 | 不直接破坏主链正确性，但形成维护或统计偏差 | 文档漂移、弱一致性、噪声 |

维度覆盖：异常逃逸 6 项；fail-fast 4 项；首帧/上游边界 4 项；并发与状态 3 项；观测 2 项；配置/启动 3 项。部分问题跨维度，只按最高影响计一次。

## 2. 问题清单（按严重度）

### 阻断

#### B1. 流消费层“宽抛、窄捕”可绕过全部终态记录

- **位置**：`/Users/vincentwang/Documents/NoteVault/tools/model_proxy/core/translate.py:245-308`；`/Users/vincentwang/Documents/NoteVault/tools/model_proxy/core/server.py:2552-2610, 2761-2792`。
- **触发**：SSE 顶层 JSON 是对象，但嵌套字段类型错误，例如 Anthropic `message_start.message="bad"`、`message_delta.delta="bad"`、`content_block_start.content_block="bad"`；三个转换 adapter 同类嵌套字段也可抛 `AttributeError`。`feed()` 的公开契约只声明/预期 `TranslationError`，实现仍直接 `.get()`。
- **证据**：最小探针稳定得到 `AttributeError: 'str' object has no attribute 'get'`；PASSTHROUGH writer 在响应已提交后复现 `_acc={status:200,response_committed:1,stream_integrity:"",...}`。生产日志新 schema 中已有 **7 条** `response_committed=1` 且 `stream_integrity` 空；其中 `7270905e`（20:12:32，`first_event_ms=63`）及 21:22 的 `bdffb6f4/ff00386b` 与该形态一致。
- **逃逸后果**：
  - probe 期：`_probe_upstream_stream()` 只捕 `pt.TranslationError`，异常越过 failover，进入 `_forward_logged.finally` 后再到 `BaseHTTPRequestHandler` 顶层，客户端收不到结构化 502。
  - committed 期：`_write_streaming_response()` 排空段完全裸奔，续读/finish 只捕 `TranslationError`；异常直接关闭上游，客户端得到“有开头没结尾”，ACCESS 仍记 200 且完整性为空。
- **修复方向**：把 framer/tracker/adapter 建成严格边界：所有外部形状先验证，内部非受控异常统一转换为带稳定 `reason/path/source_type` 的 `TranslationError`；probe 与 committed writer 再各设最后一道 `Exception→TranslationError` 防火墙，但不能用宽捕代替字段校验。`_forward_logged` 最外层增加“未提交则结构化 500/502、已提交则协议 error+终止”的请求级兜底。
- **订正种子假设**：`SSEFramer` 已将 JSON 解码错误包装成 `TranslationError`（`translate.py:222-225`）；`typ.split(".",1)[1]` 只在两个固定、必含点号的类型分支内执行，不是当前可达的 `IndexError`。真实主因是嵌套类型未校验及异常边界过窄。

#### B2. 非流式 PASSTHROUGH 不验证 JSON envelope 与业务终态

- **位置**：`/Users/vincentwang/Documents/NoteVault/tools/model_proxy/core/server.py:2124-2148`。
- **触发**：同协议上游返回 HTTP 200，但 body 非 JSON、Anthropic 缺 `stop_reason`、Responses 缺 `status`/`output`，或返回错误 envelope 却仍为 200。
- **后果**：解析块用 `except Exception: pass` 仅做 usage 嗅探，随后原样 200 写回；`status=200` 被账本计成功。P0/P1′终态语义只覆盖转换非流与四路流，没有覆盖“第四条”非流 PASSTHROUGH。
- **修复方向**：新增三协议非流 terminal validator，PASSTHROUGH 仍保留原 body 字节，但提交前必须验证 envelope、错误对象和终态；失败返回客户端协议对应 502，不得只嗅探。

### 高

#### H1. `http.client.HTTPException` 族不在网络异常边界内

- **位置**：`server.py:1509-1559, 2003-2072, 2126, 2168-2171, 2211-2214, 2257-2260, 2560-2569, 2765-2769`。
- **触发**：`HTTPResponse.read()` 抛 `http.client.IncompleteRead`，握手抛 `BadStatusLine/RemoteDisconnected` 等。它们继承 `HTTPException→Exception`，**不继承 `OSError`**。
- **后果**：count_tokens、主 `urlopen`、probe、PASSTHROUGH 续读、四条非流读取均有逃逸面；提交前表现为线程异常/无结构化响应，提交后表现为半流断开。`do_POST` 只有 `finally`，无异常出口。
- **修复方向**：transport 边界显式归一 `URLError/OSError/HTTPException`，区分 timeout、incomplete body、bad status；所有 `resp.read()` 走统一 helper，按是否 committed 决定 failover 或流内补错。

#### H2. 256 KiB“总预算”既漏计转换后增量，也物理双持 raw/framer

- **位置**：`server.py:2546-2549, 2589-2605`；`translate.py:148-171`。
- **触发**：首个业务事件接近预算，转换后编码显著膨胀。当前预算检查在 `_probe_consume_event()` **之前**，消费后立即 return，不复查；同时 `raw` 与 `SSEFramer._buffer` 各持一份原始字节。
- **证据**：200 KiB Chat 首帧实测返回 `ok=True`，`raw=200067`、`encoded=200573`、合计 **400640 > 262144**。
- **后果**：违反已确认的每 attempt 总暂存上限；并发慢流可放大内存占用。超大未闭合单帧还形成 raw+framer 双份。
- **修复方向**：采用唯一所有权 buffer（offset/view），在每次 raw append、事件消费及 encoded append 后统一检查；预算定义须明确是逻辑暂存总量还是实际 resident bytes，并按后者测试。

#### H3. 首帧 timeout 与整请求 timeout 混为 1800 秒，failover 最坏线性相乘

- **位置**：`server.py:437-440, 2539-2605, 2090-2105`。
- **触发**：每个 supply 建连成功但不产首事件；`a3a162c` 将首帧 deadline 对齐 `upstream_timeout=1800s`，每次失败后继续下一 supply/route。
- **证据**：当前配置 `cc/codex` 两 route；haiku 最多 6 个候选，理论最坏 **6×1800s=3 小时**，opus/sonnet 为 1 小时。历史日志已有 20 条 >30 分钟、最大 2,406,049ms（虽主要发生在旧实现，证明长滞留真实存在）。
- **后果**：客户端通常先在 30 分钟退出，服务端无法在预读期感知，线程和上游连接继续滞留；failover 的恢复价值被超长等待抵消。
- **修复方向**：拆分 `connect_timeout/read_idle_timeout/first_event_timeout/request_deadline`；首帧 deadline 必须受请求级总 deadline 约束，后续 attempt 只拿剩余预算。`a3a162c` 已解决 30s 误杀，但不是合理终态架构。

#### H4. 配置校验是告警而非准入，语义非法配置仍被替换上线

- **位置**：`server.py:589-617, 619-675, 736-745, 531-545`。
- **触发**：热重载合法 JSON、非法 schema；`_reload_locked()` 先 `self._config=new_config`，再校验且吞掉异常。`cooldown_rules` 虽告警“skipped”，运行时并未过滤。
- **证据**：畸形 rule `cooldown_seconds="bad"` 命中后在 `int()` 抛 `ValueError`；非 dict rule 在 `resolve_cooldown_seconds()` 抛 `AttributeError`。
- **后果**：请求热路径崩溃；旧配置没有真正保留。`upstream_timeout_seconds`、`budget_retry.max_retries` 等同样在 getter 才转换，延迟爆炸。
- **修复方向**：解析→规范化→全量验证→构造不可变 snapshot→原子替换；非法 reload 拒绝且保留旧 snapshot。容错条目要在规范化阶段真正删除，不能只打印“skipped”。

#### H5. probe 失败会把 `_acc` 中间状态泄漏到后续 supply attempt

- **位置**：`server.py:1403-1425, 1700-1703, 2092-2105, 2549`；`translate.py:263-308`。
- **触发**：PASSTHROUGH probe 已消费 usage/stop_reason/stream_content 后因后续首帧内错误失败，再 failover。
- **后果**：下一 attempt 复用请求级 `_acc`；若成功流未覆盖某字段，会把前一 supply 的 usage、stop_reason 或正文标记记到最终 supply，影响 budget_truncated 判断与账本。当前每 attempt 只新建 consumer，未隔离 accumulator。
- **修复方向**：attempt-local telemetry；probe 成功提交时一次 merge 到 request accumulator，失败只写 `attempt_errors/first_event_ms` 等 attempt 摘要。每次重试不得直接共享业务字段 dict。

#### H6. 入站 body framing 只支持 Content-Length，非法值直接逃逸

- **位置**：`server.py:1588-1606`。
- **触发**：`Transfer-Encoding: chunked`、缺 Content-Length 但有 body、非法/负 Content-Length。
- **后果**：chunked body 被当空 body继续路由；非法值在 `int()` 抛 `ValueError` 到 BaseHTTPRequestHandler；可能把错误请求转发或返回无结构化失败。
- **修复方向**：入口层明确只接受一种 framing：支持 chunked 解码，或对 chunked/冲突头直接 400/411；限制最大请求体；所有长度解析失败返回协议化 400。

#### H7. 上游流不校验 HTTP Content-Type，协议错误延迟到 body/timeout

- **位置**：`server.py:2003-2005, 2074-2111, 2539-2605`。
- **触发**：`stream=true` 上游 200 返回 `application/json`、HTML、压缩/其他媒体类型；或声明 SSE 但 body 不是 SSE。
- **后果**：小 body通常到 EOF才判坏；长连接非 SSE 可等待 1800 秒并占预算。错误归因为 `malformed_stream/timeout`，丢失 `unexpected_content_type` 证据。
- **修复方向**：提交前校验 Content-Type；允许供应商已知兼容别名须显式配置，不能无条件容忍。Content-Encoding 同步校验。

#### H8. ACCESS/账本没有“committed 流必须有 integrity”的最终不变量

- **位置**：`server.py:1427-1452, 324-370`；`_format_ops.py:332-369, 443-446`。
- **触发**：任何 B1/H1 类异常在 `stream_integrity` 写入前逃逸。
- **证据**：新 schema 877 条中，7 条 `response_committed=1 && stream_integrity=""`；日志聚合只纳入 `invalid/client_disconnect`，这些行完全不可见；账本缺 integrity 时退回 `status==200`，记为 ok。
- **后果**：最危险的异常恰好不进入 stream-integrity 看板，且污染成功率。
- **修复方向**：`_forward_logged.finally` 做不变量收口：`response_committed=1 && integrity为空` 强制记 `invalid/internal_escape`；记录 exception class/phase。账本对新 schema 不得再把 committed+空 integrity 当成功。

### 中

#### M1. Responses 非流转换默认缺失 `status` 为 completed

- **位置**：`translate.py:2336-2358`。
- **触发**：Responses body 有 `output` 但缺 status。
- **证据**：最小探针 `{output:[],usage:{}}` 得 Anthropic `stop_reason=end_turn`。
- **后果**：上游字段遗漏被静默正常化，违反未知/缺失终态 fail-fast；注释称“部分兼容网关”，但无 capability 开关。
- **修复方向**：默认严格要求 status；确需兼容的供应商使用显式 per-supply quirk，并留 ACCESS 标记。

#### M2. `stop_reason=tool_use` 与有效工具调用尚无一致性校验

- **位置**：`translate.py:976-1006, 1222-1227, 1600-1650, 1869-1896, 2398-2402`。
- **触发**：终态声称 tool_use，但无完整 tool block；或存在 tool block，终态却 end_turn。
- **后果**：客户端可能等待不存在的 tool call，或把工具调用当普通完成。
- **修复方向**：adapter/非流 validator 维护“完整工具调用数”，终态时双向校验；不完整 arguments 也应失败。

#### M3. 请求/响应 JSON 根类型约束不统一

- **位置**：`server.py:1601-1607` 及请求转换入口；count_tokens 已严格校验，主生成入口未统一。
- **触发**：合法 JSON 但根是 list/string/null，或 messages/input 内嵌类型错误。
- **后果**：不同分支出现 400、AttributeError、空请求透传等不一致结果。
- **修复方向**：入口 schema guard 至少统一根对象、model、stream、messages/input 基本类型；深层协议校验由 converter 承担并只抛 TranslationError。

#### M4. buffered 响应在 `end_headers()` 断连时逃逸，且不记录 client_disconnect

- **位置**：`server.py:2818-2832, 3130-3136`。
- **触发**：客户端在响应头发送前/中断开。`try` 只包 body write，不包 `send_response/send_header/end_headers`；`_send_json` 完全无保护。
- **日志证据**：历史 traceback 明确落在 `_write_buffered_response→end_headers→BrokenPipeError`。
- **后果**：BaseHTTPRequestHandler 打 traceback；ACCESS 可能仍写 status，但无法区分客户端断连。
- **修复方向**：统一 response writer 覆盖 headers+body，断连写结构化 outcome；非流也应有 `client_disconnect` 口径。

#### M5. 中间 attempt/budget 状态未结构化落账

- **位置**：`server.py:1417-1419, 1782-1789, 2034-2039, 2098-2105, 1432-1447`。
- **触发**：多 supply failover、budget retry、probe retry。
- **后果**：`attempt_errors` 只留内存并供最终摘要/账本计数，ACCESS 不输出逐 attempt 结构；`first_event_ms` 只保留最后一次。无法还原每 attempt 的 supply、耗时、HTTP/stream phase，定位“哪个中间态坏了”困难。
- **修复方向**：增加独立 ATTEMPT 结构日志或 JSON 数组摘要（有长度上限），请求 ACCESS 保留 final outcome；不要继续堆平铺字段。

#### M6. 旧三条 stream writer 与 `_sniff_passthrough_usage` 已被生产主链旁路，但测试仍直驱

- **位置**：生产统一流分支 `server.py:2076-2121` 已 return；旧 writer `2865-3043`、sniff `3045-3097` 仅剩不可达旧分支/测试直接调用。
- **后果**：测试对旧 helper 的绿灯不能证明统一 probe+commit 主链正确；同一协议解析保留两套实现，修复可能落错位置。
- **修复方向**：删除不可达实现及对应直接单测；handler 级测试必须从 `_forward()` 驱动真实主链，断言 ACCESS、客户端 bytes、failover 三者。

#### M7. runtime_paths 三份解析逻辑缺 schema/转义约束

- **位置**：`server.py:91-110`；`model_proxy_cli.sh:17-48`；`hooker/ensure_model_proxy.sh:13-46`。
- **触发**：值非字符串、含引号/命令替换字符、父目录不存在或 server/CLI 启动时读取到不同版本。
- **后果**：server 可在 `Path(val)` 启动崩溃；shell 通过 `eval` 注入未转义路径；三方 fallback 可能各自落到不同文件，造成“服务写 A、CLI 读 B”。
- **修复方向**：单一 Python resolver/CLI 输出 NUL 或 JSON，不用 eval；启动时强校验六个键、绝对化、目录可写性，并打印最终 resolved paths。

#### M8. 超时/失败后客户端已离开仍无法取消 probe

- **位置**：`server.py:2539-2605`；设计已明确预读期不感知断连。
- **触发**：客户端 30 分钟超时或主动取消，上游仍未给首事件。
- **后果**：在 H3 当前配置下，线程可继续至请求级数小时；形成资源泄漏式滞留。
- **修复方向**：请求级 cancellation signal 与 transport close 联动；若 stdlib handler 无可靠能力，至少以短 read-idle slice 周期检查 client socket/总 deadline，而非一次 1800 秒阻塞 read。

### 低

#### L1. `_RateLimitedLogger` 以 GIL 代替锁会丢 suppressed 计数

- **位置**：`translate.py:68-112`。
- **触发**：多请求线程同时更新同 key。
- **后果**：仅日志抑制统计不精确，不影响业务正确性。
- **修复方向**：小锁保护 get/update，或接受近似但把注释从“原子性足够”改成明确弱一致。

#### L2. 日志中的 BaseHTTPRequestHandler 连接噪声未分类

- **证据**：历史 424 个 request-handler traceback 块，主要为 326 个 BrokenPipe、59 个 ConnectionReset；大量发生在下一次 keep-alive request line 读取。
- **后果**：真实内部异常容易被连接噪声淹没。
- **修复方向**：覆写 server error handler/请求读取断连处理，常见 disconnect 降级为结构化 debug/info；内部异常保留 ERROR+req_id。

#### L3. README 日志保留说明已漂移

- **位置**：`README.md:152`仍写“末 5000 行”，实现 `server.py:113-153`已按天保留。
- **后果**：运维容量和审计窗口认知错误。
- **修复方向**：实现修复批次同步文档。

#### L4. Content-Length 与 Transfer-Encoding 出站冲突依赖 urllib 隐式处理

- **位置**：请求头复制 `server.py:1981-1994` 只剔除 Content-Length，未显式剔除客户端 Transfer-Encoding；响应侧则同时剔除二者（`2527,2747-2750`）。
- **触发**：客户端带 Transfer-Encoding，代理又设置新的 Content-Length。
- **后果**：可能向上游发送语义冲突 headers，行为依赖 urllib 版本。
- **修复方向**：出站明确删除 hop-by-hop headers（Transfer-Encoding、Connection、TE、Trailer、Upgrade 等），只生成一种 framing。

## 3. 已核实无问题/已关闭项

1. **并发写**：`UsageTotalsStore.record()` 有进程内锁且原子 replace（`server.py:267-370`）；单进程由 flock 保证。`SessionOverridesSidecar` 的 reload/read/write 均有锁与原子 replace。未发现同进程并发丢写证据。
2. **请求级 `_acc` 本身**：每个 handler 实例、每请求初始化，不跨并发请求共享；问题是同一请求多 attempt 共享业务字段（H5），不是线程串扰。
3. **未知 Responses 非流 output item**：当前已在 `translate.py:2394-2396` 抛 `TranslationError`，v4 P1 该项已完成。
4. **SSE JSONDecodeError**：公共 `SSEFramer` 已包装为 `TranslationError`；遗留 `_parse_anthropic_sse_block()` 吞坏 JSON只存在旧 helper 路径，应随 M6 删除。
5. **count_tokens 成功体**：已严格要求 object、`type(input_tokens) is int`、非负（`server.py:1560-1569`）；此项本身符合 v4。
6. **首帧 30 秒误杀**：`a3a162c` 已重启生效并恢复 opus 实流；本报告 H3 讨论的是其上位问题“首帧、整请求、failover 总 deadline 未分层”，不是要求回滚到固定 30 秒。

## 4. 建议修复分批

### 批次 0：阻断止血（必须先做，单独发布）

1. B1：外部数据形状校验；所有 parser/adapter/tracker 只向外抛 `TranslationError`；probe/committed/request 三层兜底。
2. H8：finally 不变量收口，committed+空 integrity 必判 invalid；补 7 条活体形态回归。
3. B2：非流 PASSTHROUGH terminal validator。
4. H1：统一 transport/read 异常归一，覆盖 `HTTPException`。

该批禁止顺手重构；先把“静默半途/静默成功”归零。

### 批次 1：流门卫与 deadline 终态

1. H2：唯一 buffer 所有权与真实总预算。
2. H3+M8：四类 timeout + 请求总 deadline + cancellation；failover 只消费剩余时间。
3. H5：attempt-local accumulator，成功后 merge。
4. H7：Content-Type/Content-Encoding 预检。

### 批次 2：配置与 HTTP 边界

1. H4：配置 snapshot 准入与 rollback；getter 不再做延迟类型转换。
2. H6+L4：统一入站/出站 framing、hop-by-hop header 清理、body size 上限。
3. M7：runtime_paths 单 resolver、去 eval、启动自检。
4. M4：统一 response writer 的断连分类。

### 批次 3：协议一致性与可观测性

1. M1：Responses 缺 status 严格失败，兼容行为显式 quirk 化。
2. M2：tool_use/终态一致性。
3. M5：attempt 级结构日志。
4. M6：删除旧 writer/sniff，handler 级矩阵覆盖生产调用链。
5. L1-L3：日志锁、噪声与文档清理。

## 5. 目标不变量

修复后应由代码和测试共同固定：

1. 外部输入导致的 parser/adapter/tracker 异常只能是 `TranslationError`，不得泄漏 Python 实现异常。
2. `response_committed=0` 的失败必须有非 2xx buffered error；`response_committed=1` 的流最终必须是 `valid|invalid|client_disconnect`，禁止空。
3. HTTP 200 不等于协议成功；流与非流都必须有合法终态。
4. attempt 失败不得修改 final attempt 的 usage/stop/content/terminal 字段。
5. 请求总时长不超过 request deadline，candidate 数量不得线性扩大上限。
6. probe 实际暂存总量不超过配置预算。
7. 配置 reload 要么完整生效，要么完整保留旧 snapshot。

# 风险与权衡

1. **推荐目标是边界归一而非遍地 `except Exception`**。仅加宽 except 会止住 traceback，却可能把程序 bug伪装成上游坏流；必须先做 shape validation，再在层级出口保底归类并保留 exception class。
2. **PASSTHROUGH 校验与字节透传不冲突**：可先完整验证非流 body再原样写回；流仍原样回放，只旁路维护终态。
3. **首帧 timeout 不能单点拍数**：30 秒已证实会误杀慢热上游，1800 秒×N 又不可接受。理想设计是请求总 deadline 下的分阶段预算；参数需根据 `first_event_ms` 分位数和客户端 deadline 决定。
4. **严格 status/tool 校验可能暴露供应商历史方言**：应通过显式 capability/quirk 兼容并观测命中，不能继续全局静默猜测。
5. **迁移/落地代价**：预计涉及 `server.py` transport/handler 主链、`translate.py` 三 adapter+tracker、配置 snapshot、日志 schema 和大量 handler 测试；应按四批独立发布，每批均可回滚，不因成本降低目标架构。
6. 本报告只审不改；除本设计记录外未修改仓库文件。

# 验证方式

## 1. 阻断回归矩阵

- 对 tracker 与三个 adapter 做嵌套字段类型 fuzz：dict/list/string/null/number；断言无 `AttributeError/IndexError/TypeError` 外泄。
- probe 前异常：failover on 切下一 supply；off 返回 502；ACCESS `response_committed=0`。
- committed 后异常：客户端收到协议 error+chunk terminator；ACCESS `stream_integrity=invalid`、`terminal_reason` 非空。
- 非流 PASSTHROUGH：坏 JSON、缺 stop/status、200 error envelope 均 502；合法 completed/incomplete/refused/paused/failed 按协议落账。
- `IncompleteRead/BadStatusLine/RemoteDisconnected` 在 urlopen、首读、续读、非流 read、count_tokens 五处注入。

## 2. 流与资源边界

- raw 200 KiB、encoded 200 KiB 的既有复现必须变为 `frame_too_large`；同时用内存采样断言 resident 暂存不超过预算容差。
- 单个 >256 KiB 未闭合 SSE、分隔符跨 chunk、多事件同 read、CRLF、多行 data。
- N supply 不产首帧：总耗时受 request deadline 限制，而非 N×first-event timeout。
- 客户端在 probe 第 1/10/29 分钟断开，服务端在有界时间释放线程与上游连接。
- HTTP 200 + `application/json/text/html/gzip` 在 stream 请求中提交前失败。

## 3. 状态、配置与并发

- attempt A 写 usage/stop/content 后失败，attempt B 缺这些字段但成功；最终 ACCESS 只能含 B 的事实。
- 配置热重载 fuzz：顶层/数组/元素/数值类型错误，断言旧 snapshot 保留且请求不停服。
- 100 并发请求+账本写+sidecar reload/write；核对 requests 总数、JSON 可解析、无临时文件残留。
- runtime_paths 对非字符串、相对路径、空值、引号/空格、不可写目录做 server/CLI/hooker 一致性测试。
