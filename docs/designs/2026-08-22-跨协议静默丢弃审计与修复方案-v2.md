# 背景与问题

`model_proxy` 的跨协议转换既有“静默丢弃”，也有把不支持能力伪装成普通工具、把失败或异常 EOF 伪装成成功的“伪支持”；目标是建立类型穷尽、能力显式、终态可信的转换架构，使任何关键语义损失都可见且可测试。

## v2 修订记录

本版吸收独立 architect 复核的 4 项阻断、5 项重要意见和 1 项建议，主要变化：

1. 新增 Anthropic→Responses 服务端工具被伪装成 function 的 T0 漏项，工具注册表改为双向分派。
2. P0 从简单三态扩为“终态状态 + 终止原因”，补齐 Anthropic `stop_reason` 穷尽映射。
3. web_search 门禁补齐版本化 capability 数据模型、配置校验、上下文传递和 failover 重建链路。
4. 普通 function 的 `strict` 改为双向保留，不再列为 T2 丢弃。
5. namespace 补统一 wire-name allocator、碰撞与数量上限处理；custom 补 tool_choice。
6. 补 `tool_result.is_error`、中途 system 时间语义、handler 级测试和错误分类/failover。
7. 用户已确认三个决策：未知类型分层策略、namespace 可逆扁平化、custom `{input:string}` envelope。

> [!note]
> 本文替代首版设计结论；按用户要求不修改首版文件，其 `status` 暂未标为 `superseded`。

# 方案设计

## 1. 分级与默认策略

- **T0**：失败变成功、关键工具消失或伪支持、错误结果被当成功、非法参数替换后继续执行。
- **T1**：多轮语义、终止语义或能力损失，但不必然立即报错。
- **T2**：元数据、缓存提示、展示信息损失。
- **compat-ignore**：目标协议确无语义且列入显式 allowlist 的控制事件。

用户已确认默认策略：

- 顶层未知字段：`declared_drop + 每请求结构化 warning`，避免 SDK 新增非关键字段即全挂。
- 工具类型、内容块、output item、终态事件、stop_reason：默认 reject，禁止裸 `continue/pass/default completed`。

## 3. 根因

1. 结构 union 没有穷尽分派，新增类型自然落入 `continue/pass`。
2. 转换器按字段外形而非“执行主体和生命周期”判断工具，产生静默删除和伪支持两类相反错误。
3. HTTP 200 被当业务成功，流内 failed/incomplete/error 未成为统一终态。
4. `finalize()`混合正常完成与 transport EOF，异常 EOF被合成成功。
5. ctx 只保存工具名截断，不能携带工具 identity、版本化 capability、错误 envelope 和 source/target 类型。
6. 测试固化了“未知工具删除”“异常 EOF completed”等错误契约。

## 4. 目标架构

### 4.1 TranslationContext 与错误契约

在 `core/translate.py` 定义或引用：

- `TranslationContext`：source/target、supply id、版本化 capabilities、tool mappings、wire-name mappings、loss records。
- `TranslationError`：phase、path、source type、reason、原始 error type/code/message、建议 HTTP status、是否允许 failover。
- `LossPolicy`：`convert | passthrough | declared_drop | reject`。

retry/failover 每次换 supply 必须基于该 supply 重建 context，禁止复用上一个 supply 的能力判断。

### 4.2 版本化 capability 数据模型

在 supply 增加对象而非布尔开关：

```yaml
tool_capabilities:
  function:
    version: standard
    strict: true
  web_search:
    bridge: anthropic_20250305_to_responses_v1
  mid_conversation_system:
    mode: native
```

要求：

1. `ConfigStore._validate_config()`校验 bridge/version 枚举和依赖关系。
2. `server.py`在选择 supply 后构造 capability snapshot，传入 TranslationContext。
3. 工具注册表按 source type + target protocol + bridge version 分派。
4. failover 换 supply 后重新转换整个请求，不能只换 URL/model。
5. 未声明 capability 视为不支持，不猜测。

### 4.3 双向工具注册表

新增 `/Users/vincentwang/Documents/NoteVault/tools/model_proxy/core/tool_translation.py`。每个工具注册项必须同时提供：

- 定义识别与 request encoder；
- tool_choice encoder；
- 历史 call/result encoder；
- 非流 response decoder；
- 流 response event decoder；
- capability predicate；
- strict/is_error/不可逆损失规则。

任何一面缺失，工具不可启用。

### 4.4 WireNameAllocator

namespace/custom/长工具名共用唯一 allocator：

- 只输出目标协议合法字符；上限 64。
- identity 使用完整 `(source_type, namespace, original_name)`。
- 名称格式由可读前缀 + 固定长度摘要组成；超长先按预算截可读段，再附摘要。
- 摘要算法与长度固定并有测试；请求内若生成碰撞，增加摘要长度重算，仍冲突则 400。
- 输出后禁止再次调用 `truncate_tool_name()`。
- 展开后的工具数量超过目标 supply capability 上限时，整体请求 400，不能截掉尾部工具。

### 4.5 工具语义

- **普通 function**：双向保留 description/schema/strict；strict 不支持由 capability 决定拒绝或显式降级。
- **namespace**：用户已确认可逆扁平化。子 function 分配 wire name；响应恢复 `name=<child>` 与 `namespace=<namespace>`；空 namespace、非 function 子项、数量超限均 400。
- **custom**：用户已确认 `{input:string}` envelope。tool_choice 映射到包装后的 wire name；响应恢复 `custom_tool_call`；grammar 可选本地校验，失败即 error。
- **托管/服务端工具**：只有完整生命周期 bridge 才启用。Claude Code 的 WebSearch 若形态是普通客户端工具，按 function 处理，不因名字含 web_search 被拒绝；判断依据是结构类型/版本，不是名称。

### 4.6 终态状态机

统一保存两个正交字段：

- `terminal_status = OPEN | COMPLETED | INCOMPLETE | REFUSED | PAUSED | FAILED`
- `terminal_reason = end_turn | tool_use | max_tokens | refusal | pause_turn | model_context_window_exceeded | upstream_error | malformed_stream | unexpected_eof | unknown:<raw>`

终态只能写一次。正常 EOF 只有观察到协议终态后才允许关闭；客户端断连不是上游 EOF，不得记录为 upstream failure 或触发 failover。

#### Anthropic stop_reason → Responses

| Anthropic stop_reason | Responses 终态 | 说明 |
|---|---|---|
| `end_turn`、`stop_sequence` | completed | 正常完成；stop_sequence 信息进入上下文/观测。 |
| `tool_use` | completed | output 必须存在有效工具调用，否则 failed。 |
| `max_tokens` | incomplete / `max_output_tokens` | 不得 completed。 |
| `refusal` | refused 非成功业务终态 | 若 Responses 无独立 refused wire 状态，则映射 failed，并保留 refusal 原因；需 fixture 实测定最终 wire。 |
| `pause_turn` | paused 可续跑终态 | 不得 completed；目标协议无等价时 failed，保留原因。 |
| `model_context_window_exceeded` | failed/incomplete | 按目标协议可表达能力实测决定；不得 completed。 |
| null | 仅流进行中允许 | 非流或 message_stop 前仍 null → failed。 |
| 未知值 | failed | `unknown:<raw>`，绝不默认 end_turn/completed。 |

#### Responses → Anthropic

- completed：按 output 决定 `end_turn/tool_use`，但必须校验 output 与状态一致。
- incomplete:max_output_tokens：保留部分内容，`stop_reason=max_tokens`。
- incomplete 其他原因、failed、error：Anthropic error；不得 message_stop。

改动：

错误分类：

- 请求不可接受/invalid_prompt/validation：400 或 422，不触发 supply cooldown；是否尝试同 route 其他协议 supply，由明确 `retry_class=capability_mismatch` 决定。

- rate limit：429，可按配置 failover。
- upstream internal/overloaded：502/503，可按配置 failover。
- 无法分类：502，默认不盲目重试，记录原 code/type/message。

流内失败发生在已发客户端响应头之后，不能改变 HTTP status；server 根据 TranslationError 的 retry_class 决定：若尚未向客户端写任何 SSE 字节，可尝试 failover；一旦写出，必须把 error 事件交给客户端，不能切 supply 拼接第二条流。

### P2：其余语义损失

1. 所有方向非法 arguments 禁止 `{}` 降级。
2. `tool_result.is_error` 建目标可识别 envelope；验证失败则拒绝。
3. 中途 system 按 capability 原位保留；不支持时 declared loss 或拒绝，禁止无条件提升。
4. thinking/reasoning replay 实测后注册；未验证时显式损失。
5. stop_sequences、图片 tool_result 按能力处理。
6. 顶层字段 loss summary 与 union allowlist 审计。

# 风险与权衡

1. **namespace 扁平化不是原生等价**，但用户已接受；正确性依赖 wire-name 可逆和模型遵循，必须 E2E 验证。
2. **custom envelope 改变模型看到的参数外形**，但用户已接受；必须保证回译给 codex 的仍是 custom_tool_call，而非 function_call。
3. **严格终态会把过去的“偶尔可继续”变成显式失败**。这是目标行为；异常 EOF 不应伪装成功。
4. **错误触发 failover需受首字节边界约束**：流已向客户端写出后不能跨 supply 拼流。
5. **中途 system 能力是模型/网关级而非仅协议级**，必须放 supply capability，不能全局判断。
6. **迁移代价**：需新增 capability schema、工具注册表、context、终态模型及 handler 测试；分期只控制落地顺序，不降低终态设计。
