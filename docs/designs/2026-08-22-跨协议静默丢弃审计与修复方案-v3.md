# 背景与问题

跨协议响应终态 P0 已落地并通过真实流量验证；当前需把历史方案收敛为定稿，同时补齐两项直接暴露同类风险的新能力：让 `status` 显示真实发生的跨协议链路，以及正确识别并透传 Anthropic `/v1/messages/count_tokens` 子资源。

## v3 定稿说明

- v1/v2 保留为决策演进记录，本版不修改旧文档。
- P0 改为已实施归档，不再保留待实施步骤。
- P1 遗留继续保留。
- 本期新增实施范围：A「status 协议转换提醒」、B「count_tokens 误判修复」。

# 方案设计

## 1. P0 已实施归档

### 1.1 设计要点

已在 commit `4a950a9` 实施：

- 三个转换方向统一业务终态，失败、incomplete、异常 EOF 不再伪装成功。
- `response.failed` 转 Anthropic error，error 后不再发 `message_stop`。
- Anthropic error 转 Responses `response.failed`，不再补 `response.completed`。
- `stop_reason`/`finish_reason`穷尽映射，未知值默认失败。
- malformed SSE 显式失败；协议注释帧作为 compat-ignore。
- 客户端断连与上游异常 EOF 分离。
- 非流式 HTTP 200 业务失败先校验 envelope，再进入响应转换。

结果：715 项测试全绿，三档真实流量通过。

### 1.2 两轮独立复核

**方案复核吸收 10 项**：

- 4 阻断：反方向托管工具伪支持、非正常 stop_reason、web_search capability 链路、`strict` 保真。
- 5 重要：namespace wire-name、custom tool_choice、`tool_result.is_error`、中途 system 时间语义、handler 级测试。
- 1 建议：failed 按错误类型分类，不固定 502。

其中终态与 handler 测试已在 P0 实施；工具与能力项留在 P1。

**实施复核修复 4+1 类问题**：

1. `except` 路径可能发双终态：改为终态幂等，错误后不得正常收尾。
2. Chat malformed frame 曾静默跳过：改为显式 `malformed_stream`。
3. 后续仅 usage 的 `message_delta` 曾覆写已记录 stop_reason：改为仅非空时更新。
4. BrokenPipe 一行修：客户端断连不进入上游失败终态。
5. SSE 注释帧：合法注释忽略，真正 malformed frame 失败。

### 1.3 P1 遗留

- 首帧预读：首个 SSE 字节写给客户端前允许按错误分类 failover；写出后禁止跨 supply 拼流。
- `response.output_item.added` 未知 item 类型显式 reject。
- Anthropic `stop_reason=tool_use` 与实际有效工具输出一致性校验。
- 补更完整的 handler 级矩阵测试。
- 双向工具注册表、namespace/custom、strict、托管工具 capability、`tool_result.is_error`、中途 system 等沿用 v2 P1/P2，不纳入本期 A/B。

## 2. 需求 A：status 协议转换提醒

### 2.1 数据分层

采用“静态能力枚举 + 动态 ACCESS 聚合”两层：

1. **静态层**：配置决定每个 `route × tier × supply × source` 的目标协议与转换 kind。
2. **动态层**：`.model_proxy.log` 决定窗口内实际出现的 `(token, source, route, tier, supply)` 及结果分类。
3. CLI 以动态键关联静态枚举，只显示真实发生且 `source != supply.protocol` 的组合。

不从 supply id、URL 或日志文本猜 protocol；统一使用 `resolve_protocol(supply)`，配置非法时该枚举项带明确错误，不伪装为 passthrough。

### 2.2 共享纯函数

在 `/Users/vincentwang/Documents/NoteVault/tools/model_proxy/_config_ops.py` 新增纯函数：

```text
build_protocol_conversion_hints(config) -> list[hint]
protocol_conversion_kind(source, target) -> str
```

`hint` 固定字段：

```json
{
  "route": "nation1",
  "tier": "opus",
  "supply": "openai-sol-sankuai-2023",
  "source": "anthropic",
  "target_protocol": "anthropic",
  "is_conversion": false,
  "kind": "passthrough"
}
```

约束：

- 对每个 route 的每个 tier、每个 supply，枚举 `anthropic/responses/chat` 三种 source。
- 同一 supply 在多个 route/tier 中分别保留；同一 route/tier 内重复 supply 去重。
- kind 采用稳定短名：`a2r`、`r2a`、`a2chat`、`chat2a`、`r2chat`、`chat2r`、`passthrough`。
- kind 描述“协议方向”，不代表该转换已受 `_TRANSLATOR_TABLE` 支持；动态 501 会显示为 `全501`。
- 函数不读文件、不访问 server 状态，供 server status 与 CLI 离线工具复用。

`_config_ops.py`当前顶层依赖 `_format_ops.py`；本期不让 `_format_ops.py`反向 import `_config_ops.py`，避免循环依赖。在线 formatter 直接消费 status JSON 中的 hints；未来离线命令直接调用纯函数。

### 2.3 server status JSON

在 `/Users/vincentwang/Documents/NoteVault/tools/model_proxy/core/server.py:2151` 的 `_handle_status()`增加：

```json
"protocol_conversion_hints": [...]
```

- 返回当前 ConfigStore 已成功加载配置的静态全量枚举。
- 不在 server 解析日志，不把 7 天 IO 放进控制 API。
- status 仍屏蔽 appkey。
- 配置 reload 后 hints 自然随当前快照变化；历史 ACCESS 用当前配置解释，因此 supply protocol 被改写时可能产生历史漂移，见风险节。

### 2.4 ACCESS 解析与窗口聚合

在 `/Users/vincentwang/Documents/NoteVault/tools/model_proxy/_format_ops.py`：

1. 扩展 `parse_access_line()`返回 `token`、`usage_in`、`usage_out`。
2. 新增 `load_protocol_conversion_traffic(log_path, hints, now=None, window_days=PROTOCOL_HINT_WINDOW_DAYS)`。
3. 默认常量 `PROTOCOL_HINT_WINDOW_DAYS = 7`；测试可传参，不加入业务 config。
4. 聚合键严格为 `(token, source, route, tier, supply)`。
5. builtin 行、字段缺失行、窗口外行跳过；静态 hints 找不到的历史组合不猜 protocol，也不显示。

状态分类互斥：

- `rejected_501`：`status == 501`。
- `empty`：`status == 200 and usage_out == 0`。`usage_in`单独保留用于审计，但不改变空响应判定。
- `success`：`status == 200 and usage_out > 0`。
- `other_failure`：其余 status；内部统计，避免与前三类混算。

每条记录只能进入一个桶；`n = rejected_501 + empty + success + other_failure`。

### 2.5 日志保留陷阱

当前 `/Users/vincentwang/Documents/NoteVault/tools/model_proxy/core/server.py:101` 每次启动只保留最后 5000 行，不能承诺 7 天窗口。

本期把 `_trim_log()`改为时间窗口保留：

- 保留至少 `PROTOCOL_HINT_WINDOW_DAYS + 1` 天，给时间边界留余量。
- 无法解析时间戳的尾部诊断行随最近一条日志保留；不能让 stacktrace 被单独切碎后误判。
- 仍只在启动时清理，不引入运行时轮转线程。
- 聚合返回 `coverage_start`与`truncated`供测试/诊断；定稿展示格式不新增覆盖率行。

常量必须单源。推荐在 `_config_ops.py`定义窗口常量并由 server、formatter引用；若为避免 core→CLI 常量依赖，则放中立小模块 `core/protocol_hints.py`，`_config_ops.py`仅重导出纯函数。鉴于用户指定共享函数落 `_config_ops.py`，本期优先前者，不再新建抽象层。

### 2.6 CLI 展示

在 `/Users/vincentwang/Documents/NoteVault/tools/model_proxy/_format_ops.py:596` 的 `_format_status_from_json()`中：

- 放在 active sessions 之后、cooldown 之前。
- 只显示窗口内 `n>0` 且 `is_conversion=true` 的组合。
- 按 `n`降序；并列按 token/source/route/tier/supply 字典序，保证输出稳定。
- 直通链路永不显示。
- 无转换流量时整段不打印。

定稿行格式：

```text
⚠ {token}[{source}] → {route}.{tier} → {supply}[{protocol}] ({kind}) {n}次·{失败摘要}
```

失败摘要优先级：

1. `rejected_501 == n`：`全501`。
2. `empty > 0`：`{empty}空`。
3. 全部成功：省略 `·{失败摘要}`，避免尾部悬空点。

段尾固定：

```text
跨协议链路有语义损失风险，优先用同协议原生接口直连
```

`token`沿用 ACCESS 中已脱敏的尾 4 位，不回查完整 client token。

## 3. 需求 B：count_tokens 误判修复

### 3.1 根因

`detect_source()`只识别以 `/v1/messages`结尾的 path（`server.py:842-865`）。`/v1/messages/count_tokens`不匹配，body 又常有 messages 但无 max_tokens/system，于是兜底为 chat，最终 chat→anthropic 不受支持而返回 501。

上游实测已确认 glm-5.3、gpt-5.6-sol 的 Anthropic count_tokens 端点返回 `200 + {"input_tokens": N}`。

### 3.2 协议与操作分离

不能只把 source 改为 anthropic：count_tokens 响应不是 Messages response，也不能进入 anthropic→responses/chat 转换。

新增请求操作识别：

```text
detect_operation(path) -> messages | count_tokens | default
```

规则：

- 规范化 query、大小写和尾 `/`后，精确后缀 `/v1/messages/count_tokens` → `count_tokens`。
- `detect_source()`对该精确子路径返回 anthropic。
- 其他 `/v1/messages/*`子路径维持现状：依 path 无法识别时继续 body 兜底或 unknown，不放宽为 anthropic。

### 3.3 路由约束

count_tokens 只支持 Anthropic→Anthropic：

- target supply protocol=anthropic：强制采用结构 passthrough，不进入 reasoning codec、预算 stamp、messages 响应转换或 SSE adapter。
- target protocol≠anthropic：该 supply 对当前操作不兼容。若 route `failover=on`，可继续选择同 route 后续 anthropic supply；否则返回 source 合法的 501。
- 不把 count_tokens 伪转成 Responses/Chat token 计算接口。

因此 translator mode 与 operation 共同决策，而不是给 `_TRANSLATOR_TABLE`新增伪组合。

### 3.4 target URL

新增纯函数：

```text
build_target_url(supply_url, request_path, operation) -> str
```

count_tokens 规则：

1. supply.url 必须是完整 Anthropic messages 端点，去尾 `/`后以 `/v1/messages`结尾。
2. target=`supply.url + "/count_tokens" + sanitized_query`。
3. 若 supply.url 已以 `/count_tokens`结尾，视为配置错误而非重复容错；现有 supply.url 契约仍是主请求终态端点。
4. 仅 count_tokens 操作追加后缀；所有主链路维持 `supply.url + sanitized_query`。
5. 继续剔除 `beta` query，其余 query 原样重编码。

该函数替代 `server.py:1579-1580`的裸字符串拼接；同步修订 `_sanitize_forward_query()`中“所有子路径都无意义”的过时注释。

### 3.5 请求与响应

- 请求 body 原样透传，仅按现有规则改写 model→target_model；不运行 reasoning decode/remap，避免给 count_tokens 注入无关字段。
- 鉴权头仍由代理替换为 supply appkey。
- 成功响应非 SSE，完整透传上游 status、Content-Type 与 `{"input_tokens":N}` body；记录 status，但不把 input_tokens记作生成 usage。
- 上游 HTTP 4xx/5xx：保留状态和合法 Anthropic error envelope；无法解析时用 P0 `error_body_for_source()`包装，禁止空成功。
- 若上游错误以 HTTP 200 非法 envelope 返回，校验“成功必须是非负整数 input_tokens”；否则转显式 502 Anthropic error。
- count_tokens 不触发 budget retry、reasoning 语法自适应或流式终态状态机。

### 3.6 B 的测试

在 `/Users/vincentwang/Documents/NoteVault/tools/model_proxy/tests/test_route.py`新增：

- `/v1/messages/count_tokens`、大小写、query、尾斜杠 → anthropic + count_tokens。
- 其他 messages 子路径不被新规则误收。
- target URL只对 count_tokens追加一次后缀，query净化正确。
- 主 messages/responses/chat URL保持现状。

在 handler 测试新增：

- CC 同款 body（无 max_tokens/system）不再判 chat。
- Anthropic supply 收到 `/v1/messages/count_tokens`及原 body/model rewrite。
- `200 {input_tokens:N}`原样透传。
- 200 malformed、上游 501/4xx/5xx 显式错误，不进转换器、不吞错。
- route 首个非 Anthropic supply时按 failover策略选择后续 Anthropic supply；无兼容 supply返回501。

## 4. 实施顺序与依赖

1. **B 先实施**：消除 ACCESS 中 `cc[chat]` 的 count_tokens 脏数据源。
2. A 静态 hints：`_config_ops.py`纯函数→server status JSON。
3. A 动态聚合：扩展 ACCESS parser→7 天 loader→formatter。
4. 调整日志保留，保证窗口语义成立。
5. 全量测试与真实 status 人工核对。

B 上线前的历史 `cc[chat]` 记录仍会在 7 天窗口内暂时显示并逐日自然消失；不做按日期、token 或 path 的特判。原因是 ACCESS 当前未记录 operation/path，特判只能猜测并可能掩盖真实 chat 流量。

# 风险与权衡

1. **当前配置解释历史日志**：status JSON hints来自当前配置；若 7 天内修改 supply protocol，旧日志可能按新协议解释。理想解是 ACCESS 增加 `target_protocol/kind/operation`，但本期展示要求指定以现有日志+静态 hints关联，暂不扩日志格式。建议后续把这些字段直接写入 ACCESS，消除历史漂移。
2. **7 天日志体积**：由固定 5000 行改为时间保留会增加文件大小；但这是满足需求的必要条件。若后续流量显著增长，再引入按日轮转，不能退回行数截断。
3. **失败摘要存在未定边界**：定稿格式只定义全501、空响应、成功。若同一组合出现“部分501/其他失败但无空响应”，既不能标全501，也不应标成功。建议用户补一个摘要 `N失败`；未拍板前实现应内部保留 `other_failure/rejected_501`，展示暂省略摘要但测试明确此限制。
4. **count_tokens failover**：按 operation compatibility 跳过非 Anthropic supply，不应 cooldown；它不是 supply 故障。
5. **旧脏记录**：B 修复不回写历史日志，7 天后自然消失，短期展示属真实历史事实。
