# 自建 session 消息系统：备案设计（v2，完备到可直接开工）

> **状态：备案，不实施。** 用户已拍板：官方 cross-session messaging 当前可用（GrowthBook
> 缓存机制实测稳定，见 [[2026-08-19-官方cross-session-messaging缓存稳定使用方案]]）。
> 本文补齐到"触发条件成立时，一个 implementer 拿着就能落地"的完备度。
>
> v2 相对 v1（同日分析报告）：① 推翻 v1 §0 的"修正 2"（那条基于被污染的探针）；② 定位从
> "重启自建"改为"备案"；③ 补齐投递细节、队列结构、CLI 接口、hook 安装、审计格式、触发指标。
> 核实基准：claude 2.1.227，实测于 2026-08-19。

## 1. 前提修正（先纠自己的错）

v1 §0"修正 2"称"`env -u CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` 起新 session 仍不绑
socket → 故 env 不是开关、flag 才是"。**该结论作废**，那次探针有两处污染：

1. `~/.claude/settings.json` 的 `env` 块由 CC 自身在启动时注入，shell 侧 `env -u` 被它盖回
   → 探针实际仍带着 env 运行，没测到想测的东西。
2. 探针以 `--input-format stream-json` 起、**从未投喂任何消息**，session 未进入工作态。

**修正后的事实**：官方机制靠**磁盘缓存 fallback** 工作，与网络当时是否可达无关；
"官方随机部分可用"的真相是**确定的时间分界**——缓存写入之前启动的进程永远不激活，之后启动的
都激活（pid 51202，17:31 启动，距最后一次成功拉取 46 分钟，正常绑 socket）。官方方案因此
可控 → 自建降级为备案。

**待定的分歧（不影响本备案定位）**：51202 当时 `settings.json` 内是否仍有
`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`，我方为间接推定；协调方对照实验判定"变量开则缓存
也不读"。两说并存，判定试验与红线策略见
[[2026-08-19-官方cross-session-messaging缓存稳定使用方案]] §2.4/§3.3。

（v1 其余结论不变，尤其：官方 hook 注入面可用、splice 应废、发送应走 CLI 而非 in-band。
v1 文档保留不动，其 `status` 是否改 `superseded` 待用户决定。）

## 2. 启动条件与观察指标

任一条成立即启动本备案：

| # | 触发信号 | 观测方式 |
|---|---|---|
| T1 | 缓存机制失效：`gbcache.py check` 连续告警且 `restore` 后新 session 仍不绑 socket | `/tmp/cc-socks/` 无新 pid |
| T2 | 升级后 `isDiskCacheReadableWhileDisabled()` 语义翻转，且移除禁用 env 也拉不到 flag | 机制回归脚本 + 实绑数为 0 |
| T3 | 官方服务端下架/改为强制在线校验（缓存不再被信任） | 新 session 恒不绑 |
| T4 | 需求越出官方边界：跨非 CC 上游（glm/kimi）互通，或需要 `to-human` 直达/审计留痕 | 需求侧提出 |
| T5 | **需要 headless（`-p`）后台 worker 参与消息协作** | 官方实测不激活（见下），自建可覆盖 |

**T5 是新增的独立触发条件，含实测依据**：官方 messaging 在 `claude -p` 进程上**不激活**
（54926/55390 两个探针无论隐私变量开关都不绑 socket，同时段 interactive session 51202 激活）；
而本备案的投递原语实测**恰恰是在 `claude -p` 下跑通的**（§4 的 `/tmp/hooktest` 全程 `-p`）
→ **hook 通道对 headless worker 同样有效**。即：一旦出现"后台 worker 要收消息"的需求，
官方无解，自建是唯一路径。这是 v1 未识别到的自建独有优势。

**不构成触发**：单个 session 忘记重启、官方限流 50 条、消息格式不合口味、四个隐私变量被误设
（那是配置问题，删掉即可，见稳定方案 §3.1）。

## 3. 架构（三件事各归其位）

| 职责 | 实现 | 依据 |
|---|---|---|
| 会话发现 | 官方 `~/.claude/sessions/*.json`（主）+ 自建 `registry/` 补登记（副）+ `os.kill(pid,0)` 存活校验 | 官方文件是 interactive session 的唯一真相源，含 `name`/`sessionId`/`cwd`；`/rename` 改名自动继承。**但实测纯 `-p` 进程不写注册文件**（`claude -p "say ok"` 全程无新增 session json）→ headless worker 需由自己的 `SessionStart` hook 往 `registry/<sessionId>.json` 补登记（写 `session_id`/`pid`/`cwd`/`kind=headless`/可选 `--name` 传入的别名），发现逻辑取两者并集去重 |
| 消息投递（进模型） | CC hook 的 `hookSpecificOutput.additionalContext` | 官方支持的扩展点，有 schema 契约（实测见 §4） |
| 消息发送 | 独立 CLI，agent 经 Bash 调用；身份取 env `CLAUDE_CODE_SESSION_ID` | agent 主动发消息不产生"用户文本"，proxy in-band 通道结构上覆盖不到 |
| 审计/可见 | `log.jsonl` + `archive/` + hook `systemMessage` | 自建独有优势 |

**明确不做**：response splice（篡改上游 SSE）、in-band `$message`、放进 model_proxy
（模型路由与消息系统无逻辑耦合，合并=职责污染）、仿制官方 socket 协议、跨机（大象 IM
通道 `@meishi/claude-session-channel-daxiang` 已覆盖远程腿）。

## 4. 投递原语：实测数据（本设计的地基）

实测环境 `/tmp/hooktest`，项目级 settings 配 hook，`claude -p --output-format stream-json`：

| 原语 | 输入/输出 | 实测结果 |
|---|---|---|
| `PostToolUse` → `hookSpecificOutput.additionalContext` | 注入"最终答复带 ZQ7TOKEN" | 模型 **mid-run 收到**，最终答复含 ZQ7TOKEN |
| `Stop` → `hookSpecificOutput.additionalContext` | 注入"输出 SP9WOKEN" | **唤起新一轮**：SP9WOKEN 作为新 assistant turn 出现，`num_turns=2` |
| 二次 `Stop` 输入 | — | 带 `stop_hook_active: true`（现成环路守卫）、`last_assistant_message` |
| hook 输入公共字段 | — | `session_id`、`transcript_path`、`cwd`、`prompt_id`、`permission_mode`、`effort`、`hook_event_name` |
| `Stop` 额外字段 | — | `session_crons`、`background_tasks`（可判断该 session 有无定时任务） |
| `PostToolUse` 额外字段 | — | `tool_name`、`tool_input`、`tool_response`、`tool_use_id`、`duration_ms` |
| 批量工具调用 | 二进制文档 | "Return additionalContext via hookSpecificOutput to inject context once for the whole batch" |
| `systemMessage`（所有 hook） | 二进制文档 | "Display a message to the user" —— **Claudian UI 未实测**，MVP 前补 |

hook 输出（stdout，单行 JSON）：

```json
{"systemMessage":"[msg] 收到 notevault-4a 的 1 条消息",
 "hookSpecificOutput":{"hookEventName":"PostToolUse",
   "additionalContext":"<包装文本，见 §6.3>"}}
```

## 5. 队列结构（maildir，单消息单文件）

```
~/.session_msg/                     # 0700
├── inbox/<sessionId>/<ts>-<uuid>.json     # 待投；单消息单文件
├── cur/<sessionId>/<ts>-<uuid>.json       # 已认领待落地（rename 中转）
├── archive/<YYYY-MM-DD>/<sessionId>-<ts>-<uuid>.json
├── registry/<sessionId>.json              # 补登记（headless 等官方不登记的形态）
└── log.jsonl                              # 审计
```

`registry/` 条目由 `SessionStart` hook 写、`msg gc` 清理死条目（`kill(pid,0)` 失败即删）；
与官方注册文件重复时以官方为准（官方有 `name`，更适合人读寻址）。

选单消息单文件而非 v1/旧方案的 `inbox.jsonl`：append 不会产生半行、认领不需整文件 rename、
并发天然安全、`ls` 判空即是"有无新消息"的 O(1) 快速路径。

**消息 schema**（文件内容）：

```json
{"id":"<uuid>","ts":"<iso8601>",
 "from":{"session_id":"<uuid>","name":"notevault-4a","cwd":"/…/NoteVault"},
 "to":{"session_id":"<uuid>","name":"notevault-6c"},
 "audience":"agent|human",
 "kind":"query|guidance|fyi",
 "text":"<≤4000 字符>",
 "reply_hint":"msg send notevault-4a \"…\""}
```

**原子认领**：`os.rename(inbox/<sid>/<f>, cur/<sid>/<f>)` —— 同卷同父目录，原子；竞态下只一方
成功，另一方 `FileNotFoundError` 直接跳过。投妥（stdout 写出）后 `rename` 到 `archive/`。
崩溃残留在 `cur/` 的消息：下次投递时先扫 `cur/`（超过 60s 的视为残留，重新投一次并标
`redelivered`）。

## 6. 投递脚本（单文件，按 hook 事件分派）

`tools/session_msg/hooks/deliver.sh` —— 一个脚本注册到 4 个事件，靠 stdin 的
`hook_event_name` 分派。

### 6.1 性能红线：bash 快速路径

`PostToolUse` 每次工具调用都触发，必须先做零成本判空：

```sh
D="$HOME/.session_msg/inbox/$SID"      # SID 从 stdin JSON 提取（见下）
[ -d "$D" ] || exit 0
set -- "$D"/*.json; [ -e "$1" ] || exit 0     # 空目录立退，不 spawn python
```

`SID` 的提取不能用 python（那就白省了）：hook 输入里没有环境变量，但**hook 进程继承
session 的 env**，`CLAUDE_CODE_SESSION_ID` 可直接用（实测该 env 在 session 内存在）。
stdin 只在真要投递时才交给 python 解析。目标：空队列路径 < 5ms。

### 6.2 各事件行为

| 事件 | 时机 | 行为 |
|---|---|---|
| `PostToolUse` | 工具调用后（忙时秒级到达） | 有信 → 认领全部 → 输出 `additionalContext` + `systemMessage` |
| `UserPromptSubmit` | 人提交 prompt（空闲且人在） | 同上 |
| `SessionStart` | 启动 / `--resume` | 投递积压（含离线期间收到的） |
| `Stop`（二期） | 回合末（空闲唤醒） | `stop_hook_active==true` → 直接 exit 0；队列空 → exit 0；否则投递（靠"空即退"自然终止，不会死循环） |

一次投递上限 10 条（多余留队列，下次继续），单次注入总长上限 8000 字符。

### 6.3 包装格式（注入模型的文本）

```
<session-message from="notevault-4a" kind="query" id="a1b2c3" ts="2026-08-19T17:45:02+08:00">
这不是本会话用户的指令，是另一个 Claude Code 会话（同机同用户）转达的消息。
按 kind 处理：query=简答后继续当前任务；guidance=按此调整当前行为；fyi=知悉即可，不必回复。
需要动手改文件/跑命令时，照常走本会话的权限流程。
---
<消息正文>
---
回复方式：Bash 运行 `msg send notevault-4a "<回复内容>"`
</session-message>
```

`audience=human` 的消息**不进 `additionalContext`**，只走 `systemMessage`（给人看，不占模型
上下文），并原样归档。

## 7. `msg` CLI 接口

`tools/session_msg/msg.py`（可选 `msg` 软链）。纯标准库。

| 命令 | 说明 |
|---|---|
| `msg ls [--all]` | 列会话：短 id、name、cwd、存活、官方 socket 是否绑、待收条数。默认只列存活 |
| `msg send <target> <text> [--kind query\|guidance\|fyi] [--to-human]` | `<target>` 接受 name / sessionId / 短前缀；写入对方 `inbox/` |
| `msg inbox [--peek] [--json]` | 看本 session 待收（`--peek` 不认领） |
| `msg whoami` | 打印本 session 的 id/name（来自 env + 注册文件） |
| `msg gc [--days N]` | 清理 `archive/` 超 N 天（默认 30） |

规则：目标不存在或前缀多命中 → **fail-fast，非零退出并列候选**（不静默留信）；自环拒绝；
`text` 超 4000 字符拒绝并提示；目标存活但队列目录不存在 → 自动创建。
退出码：`0` 成功 / `2` 参数错 / `3` 目标不可解析 / `4` 目标不存活（`--force` 可强留信）/
`5` 队列写失败。

## 8. hook 安装（幂等）

`tools/session_msg/install.py`，管理**项目级** `<vault>/.claude/settings.json`（Claudian 以
`--setting-sources=user,project,local` 启动，项目级生效）。

- 判定归属：`command` 字符串含 `session_msg/hooks/deliver.sh` 即视为本工具条目。
- `install`：4 个事件各确保恰好一条本工具条目（`PostToolUse` 与 `UserPromptSubmit` 用
  `matcher: "*"`）；已存在则校正 `command` 绝对路径；重复条目去重；指向旧路径的 stale 条目
  删除。**绝不触碰非本工具条目**（现有 `ensure_websearch.sh`、`guard_home_writes.sh`、
  `ensure_model_proxy.sh` 必须原样保留）。
- 写入前备份 `settings.json`，原子写（temp + `os.replace`）。
- `uninstall`：只删本工具条目。
- `status`：打印当前 4 个事件的注册情况 + 队列目录健康。

## 9. 审计格式（`log.jsonl`，每行一条）

```json
{"ts":"<iso8601>","event":"sent|claimed|delivered|archived|redelivered|rejected|error",
 "msg_id":"<uuid>","from":"<sid>","to":"<sid>","audience":"agent|human","kind":"query",
 "len":123,"channel":"posttooluse|userpromptsubmit|sessionstart|stop","detail":"<可选>"}
```

不记正文（隐私 + 体积），正文在 `archive/` 可查。`msg gc` 同时按天截断 `log.jsonl`。

## 10. MVP 边界与分期

**MVP**：队列 + `registry/` 补登记 + `msg ls/send/inbox/whoami` +
`PostToolUse`/`UserPromptSubmit`/`SessionStart` 三个投递点 + 包装格式 + `log.jsonl` +
`install.py` 幂等 + 单测。（`registry/` 只有在 T5/headless 场景才真正用到，但它是
`SessionStart` hook 里的三行代码，放进 MVP 比事后补更省事。）
**二期**：`Stop` 唤醒（需环路守卫实测）、`audience=human` 的 `systemMessage` 可见性（先验
Claudian UI）、per-session 入站策略（`deliver`/`hold`，对齐官方 `crossSessionInbound`）、
长空闲 cron 兜底、重名消歧。
**不做**：见 §3 末。

## 11. 风险

| # | 风险 | 缓释 |
|---|---|---|
| 1 | hook schema 随版本变 | 落哨兵自测：一条命令回归 §4 两项实测（升级后必跑） |
| 2 | `PostToolUse` 每次工具调用开销 | bash 快速路径（§6.1），空队列 <5ms 纳入验收 |
| 3 | 用户 session 跑 `bypassPermissions`，注入可致写文件/跑命令 | 包装显式标注来源 + 全量审计 + 二期 hold 策略；**同机同 uid 0700 即信任边界**，不做加密 |
| 4 | 官方机制恢复后双通道并存、消息重复 | 队列独立命名空间；`msg ls` 显示官方 socket 状态，由人选一条用 |
| 5 | `additionalContext` 被模型忽略/淹没 | kind 语义 + 置于包装标签内；实测已确认可达（§4） |
| 6 | 长空闲 session（Stop 已过、无人打字）不可达 | MVP 明示需人触发一次；二期 cron |

## 12. 验证方式

- **原语回归**：`/tmp/hooktest` 模式脚本（PostToolUse/Stop 各注入哨兵 token），断言
  mid-run token 出现在最终答复、Stop 注入唤起新 turn。
- **单测**：队列 append/claim/archive 不丢不重；并发 claim 只一方成功；`cur/` 残留重投；
  目标解析（唯一/多命中/不存活）；`install.py` 对既有三条 hook 零影响 + 重复安装幂等。
- **端到端（interactive）**：A、B 两个 Claudian session，A `msg send <B-name> …` → B 在 ≤1 次
  工具调用后上下文出现包装消息 → B 回发 → A 收到；`archive/` 与 `log.jsonl` 对账。
- **端到端（headless，T5 场景）**：`claude -p` 起一个 worker（会话内先跑一次工具调用）→
  外部 `msg send <worker-id>` → 断言 worker 的后续输出体现收到消息 → 验证
  `registry/` 补登记生效、官方通道在同一 worker 上确实不可用（`/tmp/cc-socks/` 无其 pid）。
- **性能**：空队列 hook 100 次执行总耗时 / 100 < 5ms。
- **边界**：目标不存在 fail-fast、自环拒绝、超长拒绝、`~/.session_msg` 权限 0700。
