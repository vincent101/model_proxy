# astra 加密块间歇解密失败与学习式剥离预案

## 0. 状态与授权边界

> **本记录是预案，不是已确认实施方案。** 用户裁决：先落文档，后续再遇到该问题时继续定位，确认根因后再调整方案并落地。本轮不改代码、不建 worktree、不部署。

## 1. 问题现象（2026-11-07 → 11-09 生产日志实证）

### 1.1 错误特征

```json
{"message": "The encrypted content gAAA... could not be verified.
 Reason: Encrypted content could not be decrypted or parsed.",
 "type": "invalid_request_error", "code": "invalid_encrypted_content"}
```

- 仅发生在 `openai-astra-sankuai-2023`（fable 档唯一 supply）
- 三天共 32 次，占同期 a2r 总量（约 50000 笔）的 **0.06%**
- **32 次全部最终 503**（fable 档无 failover 兜底）
- 每次触发后 15s～2min 自愈（下一轮请求恢复 200）

### 1.2 失败模式（时间线还原）

```text
200 (usage_in=N)         ← 正常请求
503 (usage_in=0, ~2s)    ← 紧接着的下一笔，上游预检拒绝
503 503 503 (各~10ms)    ← CC 客户端重试（同样失败）
200 (usage_in=N+增长)    ← 自愈
```

失败请求的 usage_in=0 表明上游在 token 计数前就拒绝了整个请求。

### 1.3 受影响范围

| session | 天 | 次数 |
|---|---|---|
| c906c448 | 11-07 | 12 |
| c906c448 | 11-08 | 5 |
| ddc4a138 | 11-09 | 13 |
| 02a240bd | 11-08 | 2 |

全部是 fable 档请求；session 同时有并发 subagent 跑在 sol/terra（不同 tier）。

## 2. 定位过程与已排除的假设

### 2.1 已排除：跨 supply 加密域不兼容（原假设，被实验推翻）

**直接上游实验（2026-11-09，绕过代理）**：

| 实验 | 结果 |
|---|---|
| astra 自产 enc（1720 字符）→ astra 回传 | ✅ 成功 |
| astra 自产 enc（8652 字符，取自生产 subagent 转录）→ astra 回传 | ✅ 成功 |
| **sol 产 enc → astra 回传（跨 supply）** | ✅ **成功** |
| 通过代理完整 a2r 链路：单轮 thinking 回显 | ✅ 成功 |
| 通过代理完整 a2r 链路：多轮累积 2 个 thinking 块回显 | ✅ 成功 |
| 通过代理完整 a2r 链路：streaming + thinking 回显 | ✅ 成功 |

**结论**：加密块跨 supply（sol→astra）在直接回传中可正常解密。原"sol/terra 与 astra 属不同加密域"的假设不成立，按域过滤（原方案 A 签名域标记版）会误伤。

### 2.2 已排除：代理转换损坏加密块

- 代理对 signature 只做前缀拼接/剥离（`resp:` + 原文），无 base64 重编码
- 生产 subagent 转录中的 sig 提取后直接回传成功（8652 字符验证）
- thinking 空 text + 有效 signature 的形态回传正常

### 2.3 未排除的候选根因（待后续定位）

间歇性 0.06% 失败率 + 自愈特征，指向以下方向（按可能性排序）：

1. **上游加密密钥轮换窗口**：astra 多副本部署，密钥轮换期间旧块在新副本上解密失败，轮换完成后自愈
2. **上游多副本一致性延迟**：enc 块的解密能力有副本间传播延迟
3. **特定 enc 块内容触发**：某些特定 reasoning 内容加密后的密文形态触发上游解密 bug
4. **并发请求竞争**：同 session 并发 subagent（一个打 astra、一个打 sol）在代理侧产生某种干扰（机制未明）

**定位阻碍**：错误体在日志中被截断（仅 `gAAA...` 前缀），无法对失败块的密文指纹做溯源比对。

## 3. 预案设计：学习式剥离（方案 A+B 融合）

### 3.1 设计原则

用户明确的通用性要求：**不 hardcode 某个 supply 有问题，任何 supply 出现同类失败都自动学习降级、恢复后自动回到无损状态**。

与既有 `ThinkingStripStore`（thinking 空签名剥离）和 `ToolStrictStore`（strict 策略）同一模式家族，代码结构完全复用。

### 3.2 机制

```
正常路径（未 learn）：
  客户端回显 thinking.signature=resp:<enc>
  → a2r 出站还原为 reasoning item + encrypted_content
  → 发给 supply（无损，默认行为）

失败触发（learn）：
  Responses 上游 400 且错误体含 invalid_encrypted_content
  → EncStripStore.learn(supply_id) [TTL 48h]
  → 同请求重试：出站剥离历史 reasoning item（保请求成功）
  → ACCESS 观测：enc_strip=1

learn 生效期（出站过滤）：
  该 supply 出站时剥离 enc reasoning item
  （推理历史降级为无，文本/工具历史保留——与
   "真 Anthropic thinking 跨协议丢弃"同语义）

自愈（TTL 过期）：
  48h 后 store 失效 → 回到无损默认
  若上游已恢复 → 正常工作
  若仍失败 → 首请求再吃一次 400 → 重新 learn（自愈循环）
```

### 3.3 损失评估（用户核心关切）

| 场景 | 损失 |
|---|---|
| 未 learn 的 supply（99.94% 的请求） | **零损失**——默认行为不变 |
| learn 生效期的 supply | 推理历史不回传（对话主体无损，思维链连续性降级）；对比现状是该请求直接 503 |
| TTL 过期自愈 | 无 |
| sol/terra（实测互解正常，永不触发 learn） | **零影响** |

关键对比：**现状是 503（请求完全失败）；预案是 200（请求成功，推理历史降级）**。降级仅发生在"本来就会失败"的请求上。

### 3.4 触发信号（保守设计）

learn 条件：`resp_status == 400` 且 `mode == ANTHROPIC_TO_RESPONSES` 且错误体含 `invalid_encrypted_content`。

- 错误码稳定且专指解密失败，不会误触发
- 普通参数错误、限流（429）、网络错误均不命中
- 与 thinking_strip（invalid signature）、tool_strict（strict/additionalProperties）分类器互斥

### 3.5 实施清单（确认后执行）

| 项 | 内容 |
|---|---|
| 新模块函数 | `thinking_guard.py`：`EncStripStore`（同 ToolStrictStore 结构）+ `is_invalid_encrypted_content_rejection(body)` 分类器 |
| server 接线 | ① a2r 出站转换后、发送前：learn 到的 supply 剥离 responses_body.input 中的 reasoning item（type=="reasoning" 且有 encrypted_content）；② 400 分类器命中 → learn + 同请求重试一次（与 thinking_strip retry 同模式）；③ ACCESS 增 `enc_strip` 观测字段 |
| 重试语义 | 仅一次，不 rotate/cooldown/tried_set；重试后仍失败走既有 failover/503 路径 |
| 测试 | 分类器命中/不命中、store TTL、出站剥离（learn/未 learn）、重试链路、旧格式兼容 |
| 预估改动 | ~80 行 + 测试，单 worktree 一批 |

### 3.6 与既有重试的互斥关系

| retry | mode 门控 | 分类器 | 互斥保证 |
|---|---|---|---|
| thinking_strip | PASSTHROUGH | invalid signature 文本 | mode 互斥 |
| tool_strict | ANTHROPIC_TO_RESPONSES | strict/additionalProperties | 错误文本互斥（解密失败不含这些词） |
| **enc_strip（本预案）** | ANTHROPIC_TO_RESPONSES | invalid_encrypted_content | 错误码互斥（strict 错误不含此码） |
| reasoning 语法 | 各模式 | interpret_rejection | Responses codec 恒 None |

同一 400 至多命中其一。

## 4. 后续定位计划（再遇到时执行）

1. **日志增强**：UPSTREAM_ERROR 的错误体截断长度从 ~100 提到 ~300，覆盖 invalid_encrypted_content 的密文指纹段（`gAAA...` 后 20+ 字符），用于失败块溯源
2. **失败块指纹比对**：下次发生时，从错误体提取指纹，在对应 session/subagent 转录中找到该 thinking 块的完整 signature，比对回传值是否与产出值一致（排除中间损坏）
3. **时间聚集分析**：统计失败是否聚集在特定时间窗（支持密钥轮换假设）
4. **并发关联**：失败时同 session 是否有并发请求打到不同 supply（支持并发竞争假设）
5. 若根因确认为上游侧（密钥轮换/副本一致性）：本预案即最终方案；若发现代理侧可修的点（如某形态处理不当）：先修根因再评估预案是否仍需要
