# 官方 cross-session messaging 对比与自建重启方案（[理想] 路径）

> 核实基准：2026-08-19，claude 2.1.227（brew cask），本机 6 个活 sdk-ts session，
> model_proxy master。所有结论带实测口径，未实测项显式标注。

## 0. 前提核查（两处修正，先于方案）

**修正 1：官方机制不是"全锁死"，是"随机部分可用"。**
`~/.claude/sessions/` 6 个活 session 中，**2 个**（procStart 08:43 / 08:49）带
`messagingSocketPath: /tmp/cc-socks/<pid>.sock`，socket 实际 listen 中（`lsof -U` 显示
claude 进程持有 fd，AF_UNIX connect 成功）；其余 4 个（02:36–03:32 启动）该字段缺失、
无 socket。同版本、同 cwd、同 entrypoint。

**修正 2：`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` 不是唯一开关。**
实测：`env -u CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` + 2.1.227 + sdk-ts 起新 session
（pid 46559）→ 注册文件正常写入，**socket 仍不绑**。故绑定由 flag 决定，env 只是另一道
闸；flag 结果按**进程启动瞬间的网络运气**固化，进程生命周期内不再变。

**对决策的影响**：自建结论不变，但理由要改。不是"官方永远拿不到"，而是"官方**不可控地
只覆盖随机子集**"——ListAgents 只看得见幸运的那几个 session，主会话与并行 session 谁能
互通不由用户决定。对"多 session 协作"这种需要**全员可达**的场景，随机部分可用比全不可用
更糟（会给出假的可达感）。**自建成立。**

## 1. 关键新发现：官方 flag 之外另有官方支持的注入面（已端到端实测）

2.1.227 二进制内嵌 hook 文档 + `/tmp/hooktest` 端到端实测（`claude -p` + 项目级 hook）：

| 原语 | 实测结果 |
|---|---|
| `PostToolUse` → `hookSpecificOutput.additionalContext` | **模型 mid-run 收到**。注入文本要求"最终答复带 ZQ7TOKEN"，最终答复出现 ZQ7TOKEN |
| `Stop` → `additionalContext` | **唤起新一轮**。注入"输出 SP9WOKEN"，SP9WOKEN 作为新 assistant turn 出现，`num_turns=2`；二次 Stop 输入带 `stop_hook_active: true`（环路守卫现成） |
| hook 输入 | 自带 `session_id` / `transcript_path` / `cwd` / `permission_mode`；Stop 另带 `session_crons` / `background_tasks` |
| `systemMessage`（所有 hook） | 二进制文档标为"Display a message to the user"，**Claudian UI 未实测** |

**这两条把 shelved 方案最硬最脆的一段整体作废**：Step 8–11 的 response splice（
PASSTHROUGH 流式升级为事件级、index 跟踪、幂等闸门、失败降级）不再需要——官方投递点
就是官方自己 mid-turn 投递用的那个位置，且有版本化 schema 契约。

## 2. 官方功能清单：核心 vs 锦上添花

**用户真需要的核心**（同机、多 session、发现+传话+请求对方做事）：
① 会话发现（注册文件 pid/sessionId/cwd/name）；② mid-run 投递（工具间隙，不打断）；
③ 空闲投递（开新 turn）；④ 消息带发送方名 + 回信地址；⑤ 纯文本语义、接收方 turn 间隙读；
⑥ 防环 + 积压上限。

**锦上添花**：`crossSessionInbound` 三态 × 权限模式分治、hold 5min 过期、`@`提及、
agent teams roster、100 万字符上限、跨机 Remote Control（用户已有
`@meishi/claude-session-channel-daxiang` 覆盖 IM 远程腿，无需重建）。

**卡点**：①②③ 全部挂在同一个 flag 上，不可控（§0）。而②③的**投递能力本身**在 hook 面
是可用的（§1）——即"官方能力被 flag 锁住的部分，恰好在官方另一个未被 flag 锁的扩展面上
可以自建"。

## 3. 三篇 shelved 方案覆盖度（逐功能）

| 功能 | 官方（flag 通时） | shelved 自建 v3.1 | 评估 |
|---|---|---|---|
| 会话发现 | ListAgents（仅绑 socket 的子集） | proxy 进程内"见过的 session"表 + 短 id | 自建弱：proxy 重启即失忆，且只见"发过请求"的 session。**应改用官方注册文件** |
| 寻址 | name（/rename、--name） | 裸 sessionId + 前缀匹配 | 自建弱：人不可读。官方 name 免费可继承 |
| mid-run 投递 | 工具间隙注入 | 通道 b：请求体追加 text block + 响应流 splice 回执 | 自建**过度复杂且脆**：改上游请求 + 篡改 SSE 字节流。已被 §1 PostToolUse 取代 |
| 空闲投递（人在） | 开新 turn | 通道 a：UserPromptSubmit hook | 等价，保留 |
| 空闲投递（人不在） | 开新 turn | agent 自建 CronCreate 轮询 `$message check` | 自建弱（10min 延迟 + transcript 噪声）。§1 Stop 唤醒可覆盖"回合末"，长空闲仍需 cron |
| 离线/重启补投 | — | SessionStart hook | **自建独有**，保留 |
| 可见性 | transcript 内联 | splice 回执 + delivered 归档 + ACCESS 日志 | 审计自建更强；可见性用 `systemMessage` 即可，不需 splice |
| 发送入口 | Claude 调 SendMessage 工具 | in-band `$message send`（proxy 拦截用户消息） | **自建路径有硬缺陷**：proxy 只看得到请求体里的用户文本，agent 主动发消息不产生这种文本 → in-band 通道天然只服务"人打字"，覆盖不了 agent→agent。应改为 CLI + Bash 工具调用 |
| 入站控制 | crossSessionInbound 三态 + 权限模式分治 | 无（只做包装标注） | 自建缺口。二期补 per-session policy |
| 安全边界 | 消息不能批权限/改配置/执行斜杠命令 | 同信任面（能发请求即可投递） | 用户 session 跑 `bypassPermissions`，注入放大风险真实存在，需审计 + 标注 |
| 消息类型 / to-human | 纯文本、总给 agent | query/guidance + to-human 直达 | **自建独有**，保留 |
| 跨非 CC 上游（glm/kimi） | 不支持 | 支持（proxy 层） | 自建独有，但**当前无需求**，不值得为它选 proxy 通道 |
| 跨机 | Remote Control（经 Anthropic） | proxy + IM 桥 | 已被大象通道覆盖，出局 |

**一句话**：shelved 三篇的**需求分析与状态覆盖矩阵（四通道）仍然正确且有价值**，
但它的两个通道选择（in-band `$` 发送、splice 投递）都是在"当时以为没有官方注入面"的
前提下做的绕路，现在前提变了，这两处应被推翻。

## 4. 推荐重启路线

**方案 C（推荐）：官方注册文件做发现 + 官方 hook `additionalContext` 做投递 + 独立 CLI 做发送，
作为 model_proxy 之外的独立小工具。**

对比：
- **方案 A（复活 shelved 三篇）**：splice 篡改上游 SSE 字节流 + in-band 发送。否决——
  发送通道覆盖不了 agent→agent（硬缺陷），投递通道复杂度与脆性都远高于 §1 原语。
- **方案 B（自建 socket 仿制官方协议）**：否决——官方 socket 只是传输，真正的难点是
  "消息如何进入模型上下文"，那部分在 CC 内部、flag 后面，仿不了。（附注：对已绑 socket 的
  那 2 个 session，自建 sender 理论上可投官方 socket，但可达性随机 → 不能当地基。）
- **方案 C**：见下。

**选 C 的理由（按技术设计优先级）**：
1. 架构合理性：投递走官方**有 schema 契约的扩展点**，不篡改上游响应；发现复用官方**唯一
   真相源**（`~/.claude/sessions/`），不再维护第二份会话表（消除 DRY 违背与"proxy 重启失忆"）。
2. 长期扩展性：CC 升级时 hook 契约稳定性 >> SSE 篡改的稳定性；官方 flag 若哪天通了，本系统
   与之**并存不互斥**（不同队列命名空间），不需要推翻。
3. 场景兼容性：一个脚本按 `hook_event_name` 分派，覆盖 sdk-ts/Claudian、`-p` headless、
   subagent 同一条路；退化情况（空闲/离线）是一般情况的特例。
4. 与 model_proxy 的关系：**不进 model_proxy**。model_proxy 的职责是模型路由与协议转换，
   消息系统与之无逻辑耦合，塞进去是职责污染；且 in-band `$` 通道天然只服务人打字（§3）。
   落点建议 `tools/session_msg/`（独立嵌套 repo，对齐 model_proxy 拆分先例 + 外层 .gitignore）。
   代价：model_proxy 现有的 ACCESS 日志/session 表复用不到，需自带审计——可接受，换来职责单一。

**关键设计点**：
- **队列**：`~/.session_msg/inbox/<sessionId>/<ts>-<uuid>.json`，**单消息单文件**（maildir），
  `rename` 到 `cur/` 原子认领，投妥后落 `archive/<date>/` + `log.jsonl`。相对 shelved 的
  `inbox.jsonl`（append 半行风险、并发认领要整文件 rename）更简单更稳。目录 0700。
- **发现**：读 `~/.claude/sessions/*.json` + `os.kill(pid,0)` 存活校验；寻址优先官方 `name`
  （`/rename` 改名自动继承），次选 sessionId 短前缀；歧义 fail-fast 列候选。
- **投递**：单脚本按 `hook_event_name` 分派——`PostToolUse`（忙时秒级）/ `Stop`（回合末唤醒，
  守卫 = 队列空即退 + `stop_hook_active`）/ `UserPromptSubmit`（空闲且人在）/ `SessionStart`
  （重开补投）。输出 `additionalContext`（给模型）+ `systemMessage`（给人）。
- **性能红线**：`PostToolUse` 每次工具调用都触发 → 必须纯 bash 快速路径，空队列
  （`ls` 目录判空）立即 exit 0，**不 spawn python**；仅有信时才走完整投递。
- **发送**：CLI `msg ls | send <target> <text> [--kind query|guidance] [--to-human] | inbox`。
  发送方身份取 env `CLAUDE_CODE_SESSION_ID`（本机实测存在）。agent 经 Bash 调用，人则直接说
  "告诉 X ⋯"（与官方 SendMessage 手感一致）。
- **安全边界**：信任面 = 同 uid 同机（0700）。包装显式标注"非本会话用户指令 / 来源 session"；
  用户 session 跑 `bypassPermissions`，消息可间接导致写文件/跑命令 → MVP 靠"标注 + 全量审计
  日志"，二期补 per-session `deliver/hold` 策略对齐官方 `crossSessionInbound`。斜杠命令、
  配置改动一律当纯文本，不解释执行。

## 5. MVP 边界与分期

**MVP（做）**：队列 + `msg ls`（含存活/官方 socket 状态列）+ `msg send` +
`UserPromptSubmit`/`PostToolUse`/`SessionStart` 三个投递点 + `log.jsonl` 审计 + hook 安装
幂等管理（复用 model_proxy `_install_ops` 的思路，代码不共享）。
**二期**：`Stop` 唤醒（需环路守卫实测）、`to-human` + `systemMessage` 可见性、per-session
入站策略、长空闲 cron 兜底、重名消歧。
**不做**：response splice、in-band `$message`、跨机（大象通道已覆盖）、跨非 CC 上游、
官方 socket 仿制。

**处置建议**（需用户确认后由他人执行，本文不改动他文）：三篇 shelved 文档改
`status: superseded`、`superseded_by` 指向本文；其"四通道状态矩阵"与实测证据在本文引用后
仅作史料。

## 6. 风险与权衡

| # | 风险 | 缓释 |
|---|---|---|
| 1 | hook schema 随 CC 版本变 | 落一个哨兵自测脚本（对齐 `MEMTECH_V1` 做法），升级后一条命令回归 §1 两项实测 |
| 2 | `PostToolUse` 每工具调用开销 | bash 快速路径 + 实测空跑耗时纳入验收 |
| 3 | `bypassPermissions` 下注入放大 | 标注 + 审计 + 二期 hold 策略 |
| 4 | 官方 flag 恢复 → 双通道并存重复投递 | 队列独立命名空间；`msg ls` 显示官方 socket 状态供人判断 |
| 5 | `systemMessage` 在 Claudian UI 未验证 | MVP 前补一次实测；退路：可见性靠 CLI stdout + 模型复述 |
| 6 | 长空闲（Stop 已过、无人打字）不可达 | 二期 cron；MVP 明示该状态需人触发一次 |

**落地代价（理想路径提示，不因代价改设计）**：新起一个独立工具（约 3 个文件：queue+CLI、
hook 脚本、安装器 + 单测），shelved 三篇的 16 步实施计划中约 Step 7–11、14 的 splice/注入
部分（工作量最大的一段）作废、不可复用；可复用的是需求分析、四通道矩阵、maildir 与 hook
安装幂等的经验。总工作量估计**低于**原计划一半。

## 验证方式

- **§1 原语回归（可复跑）**：`/tmp/hooktest` 模式——项目级 settings 配 `PostToolUse` +
  `Stop` hook，各返回一段带哨兵 token 的 `additionalContext`，`claude -p --output-format
  stream-json` 跑一轮，断言最终答复含 mid-run token、且出现由 Stop 唤起的新 assistant turn。
- **官方可用性快照**：`for f in ~/.claude/sessions/*.json` 打印 `messagingSocketPath` +
  `lsof -U | grep cc-socks`，记录"几个 session 可达"，作为自建必要性的持续证据。
- **端到端**：A、B 两个 Claudian 会话，A `msg send <B-name> …` → B 在下一次工具调用后
  （≤1 tool call）上下文出现包装消息 → B 回发 → A 同样收到；`archive/` 与 `log.jsonl` 对账不丢不重。
- **性能**：空队列下 hook 脚本 100 次执行总耗时，单次目标 < 5ms。
- **边界**：目标不存在 → fail-fast 列候选；自环拒绝；超长截断；目录 0700 校验。
