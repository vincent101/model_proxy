# model_proxy C 档螺旋与 B+ 收敛复盘

> 一句话：为防 <1% 的上游坏流（空流/断尾），代理走上了 C 档强防护路线（首帧预读+流级 failover），自造的副作用（30s 误杀 9.6%、预读族 bug）远超收益；数据复盘后做减法退回 B+（即时提交+旁路观察+EOF 善后），复杂度与上游真实质量对齐。

## 关键决策依据

### 为什么选 B+ 而非 C

数据（一周日志 18,279 条）：

| 复杂度族 | 真实频率 | 判定 |
|---|---|---|
| HTTP 429/5xx failover | 3,086 次 attempt | 代理核心价值，保留 |
| 流断尾（200 坏流） | 8/1,298 = 0.62% | 真实但低频 |
| 首帧预读副作用 | 125 条误杀 = 9.6% | 为防 0.62% 制造 10%，失衡 |
| 审计 22+8 项中 11 项 | 零生产证据 | 纯理论保险，降级为观察 |

C 档继续修要 10 项前置（ProxyError 契约/attempt 隔离/三层边界）——架构级建设，且机制在就有新 bug 面。B+ 一次拆净，机制消失即税清零。

### 为什么不选 A（最大透传）

0.62% 的坏流直通会让 Claudian turn 挂住（需手动 ESC）。B+ 的 EOF 善后把这 0.62% 从"不明不白挂死"变成"明确报错+直接重发"——加几十行代码换掉手动操作，性价比高。

### B+ 的边界界定（防滑回 C）

- **不干预活流**：无预读/无缓冲/无中途断流/无换家——这是 C 档复杂度之源
- **只善后死流**：EOF 时判定终态是否到达，未到则补协议 error 给 SDK 再收尾——流已死，补错零破坏
- **旁路观察零控制权**：observer 异常只记日志（observer_error），绝不影响转发

## 方法论提炼

### 1. 数据先行再开机制
事故驱动决策时容易"见到一次就上防护"。先看频率：0.62% 的事故值不值得为它开一套机制，机制的副作用（9.6%）是否高于它防的事故。**没数据就先观察（enforcement=false），有数据再开机制**——这次软阈值冷却就是这么设计的。

### 2. 修复螺旋识别
"防 A 引入 B，修 B 引入 C"——6dec90a→30s 误杀→a3a162c→审计发现预读族一堆 bug。识别信号：每次修复都在同一套复杂机制上施工，且每次新引入的边界比修掉的多。**看到螺旋时，停下来问"这套机制本身是不是问题"**，而不是继续在机制里打补丁。

### 3. 做减法是合法选项
复杂度不是资产。机制在就有维护税、就有新 bug 面。当数据证明"机制的副作用 > 它防的事故"，撤退（做减法）比继续加固正确——即使已经投入了建机制的成本（沉没成本不参与决策）。

### 4. 责任边界划分
- 代理：HTTP 级容灾（429/5xx/网络 failover）+ 跨协议转换 + 死流善后报错
- Claudian：坏流来了不死（lease 不泄漏、attention 不悬挂、Stop hook 不卡）
- 上游：质量本身（报障修复后，0.62% 预计还会降）

**不要让代理替上游兜底救回当前请求**——那是 C 档，是过度责任。

## 最终架构（B+）

```
客户端请求 → 选家 → 上游非 2xx？→ failover 换家（429/5xx/网络，主力容灾）
              ↓ 2xx
         立即提交，纯字节透传（无预读/无缓冲/无超时门槛）
              ↓ 旁路
         observer 只记不说：终态完整性/usage/健康计数（enforcement=false）
              ↓ 流结束时
         有终态→原样收尾 | 空流/断尾→补明确 error 给 SDK（你直接看到报错，不再挂住）
跨协议链路：保留转换+P0 终态校验，200 后不换家
```
