# 正文错误识别（body error）与 failover/cooldown 衔接方案

## 0. 背景与问题

mcli 系 supply（`https://mcli.sankuai.com/v1/messages`，全部 `protocol: anthropic`，
走 anthropic→anthropic PASSTHROUGH）在上游报错时返回 **HTTP 200 + 正文携带错误文本**。
现有失败判定只认 HTTP 状态码与网络异常，对"200 但语义是错误"零感知：错误文本被当
正常模型回复透传给客户端，supply 不冷却、不轮转，当前与后续请求持续打在同一故障源。
两条实测样例：

1. `当前小时请求过于频繁，请下个整点重试`（限频类）
2. `本次请求未命中任何路由策略，且当前场景未配置兜底模型。`（路由未命中，配置类）

目标：识别这类响应，映射为可轮转/降级语义（supply 冷却，跨请求自动规避；非流式
场景同请求 failover），新增错误文案的配置成本一行。

## 1. 调研结论（文件:行号）

### 1.1 失败判定与轮转链路

- 唯一失败判定入口：`core/server.py:2287-2352`（`_forward` 内 `urlopen` try/except）。
  `HTTPError` → `resolve_cooldown_seconds(resp_status, cs)`（`:778`）查顶层
  `cooldown_rules` → 命中且 `route.failover=="on"` → `cd.cooldown(supply_id, secs)`
  （`:742`）+ `tried_set.add` + `continue` 回 `while` → `select_supply`（`:1160`）
  跳过 tried/cooling 取下一 supply，**同请求内换源重发**。`URLError` 同构
  （errorcode 字符串 `"URLError"`）。未命中规则 → 透传 + `_record_unconfigured`
  （`:796`）记账。全耗尽 → 503 + attempt_errors 拼进 err_summary（`:2531-2550`）。
- `cooldown_rules` 形状（example.json:5-11）：
  `{"errorcode": [int | "URLError"], "cooldown_seconds": N}`——errorcode 已支持
  字符串命名空间，新虚拟 code 零改动兼容。

### 1.2 既有 200-后内容判定先例：④b 预算重试的"双轨"形态（本方案直接对标）

`_maybe_budget_retry`（`server.py:2015`）已确立"非流式 200 响应内容判定"的合法形态：

- **非流式**：`resp.read()` 之后、写回之前判定，命中则 `continue` 重进 while 重发
  （PASSTHROUGH 插点 `:2369`；转换路径三处同款 `:2405/:2448/:2494`）。
- **流式**：字节即时下发、发出后无法回追——**只在收口处检测记
  `budget_truncated` 日志，不重试**（README「已知限制」明文，`:2360-2363`）。

正文错误识别完全复制这个双轨：非流式判定+重试，流式收口记账+跨请求冷却。

### 1.3 B+ 架构裁决（2026-08-24，本方案的硬边界）

`2026-08-23-最小可靠透传重构方案-v2`（confirmed）与
`2026-08-24-modelproxy-C档螺旋与B+收敛复盘`（closed）拍板：

- 流式 PASSTHROUGH **即时提交、纯字节透传：无预读、无缓冲、无中途断流、无换家**
  （C 档首帧预读+流级 failover 曾上线后被数据否决：30s 超时误杀 9.6% vs 坏流事故
  0.62%，预读族连出 bug；`259c60e/1990fd3` 已删除 probe 与缓冲链路）。
- observer 旁路只记不说（enforcement=false）；只善后死流（EOF 无终态补 error）。
- "**不要让代理替上游兜底救回当前请求**"。
- ④b（非流式 200 判定重发）在 B+ 收敛中被保留——B+ 拒绝的是**活流**干预与预读
  复杂度，不是非流式内容判定重试。

结论：**流式正文错误识别不得采用"提交前预读闸门"（C 档复活）**；正确形态是
④b 同款的流式分支——旁路累计、收口判定、跨请求冷却、不干预已透传字节。

### 1.4 流式旁路观察的现成挂点

`PassthroughStreamObserver`（`core/translate.py:242`）+
`PassthroughTerminalTracker`（`:283`）已逐事件解析 SSE：终态/usage
（`_usage` :355）、text/tool 内容块标记 `stream_content`（`:335`）。累计 text 全文
与 tool/thinking 结构标记只差几行 feed 逻辑；判定挂点即
`_write_streaming_response` 的 `observer.finish()` 收口（`server.py:2803`）。

### 1.5 wire 形态（待实测取证）

客户端把错误文本**当正常回复显示**（非 API error 样式），推断主形态为
"SSE 正常结构 + text 内容块携带错误文本"（终态 valid，现有链路完全无感知）；
次要可能为 200 + 纯文本/非 SSE JSON。实施前 curl 复现一次校准（§5 R1）。

## 2. 方案设计

核心思想：**正文错误 = 产生虚拟 errorcode（`body_*`），走既有
`resolve_cooldown_seconds → cd.cooldown` 链路**；非流式额外复用
HTTPError 分支的 `tried_set + continue`（④b 同款位置）。不新造状态机、
不新造冷却通道、不动流式提交时序。

### 2.1 配置形状（主 config 顶层新键，无独立文件）

```json
"body_error_rules": [
  {"pattern": "当前小时请求过于频繁", "match": "contains", "errorcode": "body_rate_limited"},
  {"pattern": "未命中任何路由策略", "match": "contains", "errorcode": "body_route_miss"}
],
"cooldown_rules": [
  {"errorcode": [429, "body_rate_limited"], "cooldown_seconds": 3600},
  {"errorcode": [401, 402, 403, "body_route_miss"], "cooldown_seconds": 21600}
]
```

**cooldown 示例为合并式推荐形态（用户拍板 2026-10-10）**：`body_*` 虚拟 code 与同语义 int code 同行（首条命中顺序语义正确）。注意用户现有配置中 429 已在 60s 规则行（`[429,500,502,503,504]→60`）——实施时把 `body_rate_limited` 并入哪一行、是否随之调整 429 时长，由用户落地时自定；本设计只固化"合并式为推荐形态"。

- 无 `body_error_rules` 键或空数组 = 功能整体关闭，零行为变化（对齐 budget_retry
  缺省启停风格，fail-open）。
- `match`：`contains`（默认）| `exact` | `prefix`。不做 regex（ReDoS 面 + 无需求）。
- 冷却时长只在 `cooldown_rules` 配（**冷却时长单一来源**）；`body_*` 前缀与
  int code / `"URLError"` 命名空间区分，`resolve_cooldown_seconds` 查表与
  `_record_unconfigured` 记账零改动复用。
- **加新错误文案 = `body_error_rules` 加一行**；新行为类别才需 cooldown_rules 加行。
  mcli 升级改文案 = 改一行 pattern。
- `ConfigStore` 增 `get_body_error_rules()`（`:538` 旁）+ `_validate_config` 容错校验
  （非法 rule log warning 跳过，同 `_validate_cooldown_rules` :656 风格）。
- **校验同步放开（复核中1）**：`_validate_cooldown_rules` 元素校验
  （`server.py:675-679`）现只认 `int | "URLError"`，合并式行含 `body_*` 字符串会
  每次加载/热重载刷 warning（不阻断但持续噪声）。实施时改为**"int 或任意非空
  字符串"**，不特判 `body_*` 前缀——理由：特判则每引入新虚拟 code 前缀都要同步
  改校验，违背"加规则一行成本"目标；且 errorcode 命名空间本就开放
  （`_record_unconfigured`/`resolve_cooldown_seconds` 均按任意值处理），
  校验收紧无安全收益。

### 2.2 识别函数（纯函数，`core/server.py` 模块级）

```python
def match_body_error(text: str, rules: list[dict], *,
                     saw_tool_or_thinking: bool, text_len: int) -> str | None
    """返回命中 errorcode；未命中/结构条件不满足返回 None。"""
```

**误伤防护——结构条件三条全部满足才判错误**：

1. 响应无 `tool_use`、无 `thinking` 块（错误响应没有；正常回复一旦开始思考/调
   工具即排除）；
2. text 全文长度 ≤ `max_text_len`（默认 200 字符，rule 级可覆盖；样例 ~20/~30 字）；
3. 模式按 match 档命中。

性能：条件 2 先行短路——超限一次整数比较即出；短响应才做个位数模式 `str.find`
（µs 级）。流式放行后不回头扫（对齐 ④b 流式语义）。

误伤残余（模型恰好只回一句错误文案）：后果 = 非流式一次重发 / 流式一次跨请求
冷却，可恢复非永久，接受；讨论错误文案的正常回复被条件 1/2 绝大多数拦截。

### 2.3 非流式插点（Phase 1：PASSTHROUGH；Phase 2：转换路径三处）

`server.py:2369` `resp_body = resp.read()` 之后、`_maybe_budget_retry` **之前**：

```
text = 提取正文：json.loads 成功且 content[].text 非空 → 拼接 text；
      否则（JSON 合法但无 content text——错误文本在 error/顶层字段、content 空，
      或 JSON 解析失败）→ raw UTF-8 解码全文兜底（复核轻5：兜底条件是
      "无 content text"而非仅"解析失败"，覆盖 JSON 合法的错误字段形态）
code = match_body_error(...)
if code: → HTTPError 分支同款四连（log.warning + _acc failover/attempt_errors +
          cd.cooldown + tried_set.add）+ resp.close()（复核轻4，对标 :2370-2372
          budget_retry 命中后 close+continue 既有模式）+ continue
```

客户端零感知（未发出任何字节，代理干净换源重发）。命中但 cooldown_rules 未配
该 code → `_record_unconfigured(code)` + **原样写回 `resp_body`**（复核中3：不走
`error_body_for_source`——它需真实非 2xx status，传 200 会产出 200+proxy error
体的畸形响应；原样写回是真 fail-open，客户端看到的就是上游原文，语义对齐
HTTPError 未配分支"透传+告警"）。

**B+ 合规性**：无活流、无拼接（重发后客户端只见一个完整响应）、无预读缓冲
（非流式本就全量 read）——B+ 否决的三要素均不涉及；④b 已确立该位置重发的
合法性，本方案仅把"同 supply 重发"扩为"换 supply"（限频类同 supply 重发必然
再撞，换源才有意义）。

### 2.4 流式插点：旁路收口判定 + 跨请求冷却（B+ 对齐，当前请求不救）

不改 `_write_streaming_response` 提交时序（`:2771` 进函数即提交头），改动全部
在旁路与收口：

1. `PassthroughTerminalTracker.feed` 增量累计：text 全文（`content_block_delta`
   的 `text_delta.text`）、tool/thinking 出现标记（`stream_content` :335 旁并列）。
2. 判定统一挂 `_write_streaming_response` 的 **`finally` 块**（`:2825`，`resp.close()`
   旁；复核中2：正常路径 `observer.finish()` 在 `:2803`，但客户端断开
   （`:2820` BrokenPipe/Reset 分支）与上游读错（`:2788` OSError 分支）提前
   return 时 finish() 不执行——挂 finish 后则这两类退出不判定、不冷却；挂
   finally 则全部路径收敛判定）。**幂等护栏**：`_acc["body_error"]` 已置则跳过，
   防正常路径（finish 已跑、finally 再跑）双跑。
   `code = match_body_error(累计 text, ...)` → 命中：
   - `cd.cooldown(supply_id, secs, code)`——supply_id 取
     `self._acc["supply"]`（复核轻7：该函数签名无 supply_id 参数；`:2094` 每轮
     attempt 已把当前 supply_id 写入 `_acc`）；secs 经
     `resolve_cooldown_seconds(code, cs)`，handler 可达
     `self.server.cooldown_store/config_store`；
   - `_acc["body_error"] = code`（ACCESS 新字段）+ `final_error` + `log.warning`；
   - **不补 error 事件、不改已透传字节、不重试**（活流已完、终态正常，补错属干预）。
   - 未配 cooldown → `_record_unconfigured(code)`，只记不冷却（对齐 HTTPError 语义）。
3. **提前退出路径的漏判面（挂 finally 的残余限制，如实声明）**：上游读错发生
   在错误文本尚未传完时，累计 text 不完整——contains 匹配对不完整前缀 fail-open
   漏判（退化现状，无误伤放大，可接受）。客户端断开场景错误短文本通常已全部
   累计（每 chunk 先写客户端再喂 observer，断开前已 feed 的部分保留），判定有效。
4. 本次请求如实交付错误文本（客户端可见一句错误文案）；**下一条请求起
   `select_supply` 自动避开该 supply**（cooldown 驱动）——自愈路径。

用户实际体验：限频撞上 → 当前回复是一句错误文本 → 下一条消息已换 supply。
非挂死、非循环，B+ 边界内最优。当前请求不救的代价与升级选项见 §3。

### 2.5 错误类别 → 行为映射

| 类别 | errorcode | 非流式（Phase 1） | 流式（Phase 1） | cooldown | 对标 |
|---|---|---|---|---|---|
| 限频 | `body_rate_limited` | failover 换源重发 | 收口冷却，下请求换源 | 3600s（与 429 合并行） | HTTP 429 |
| 路由未命中 | `body_route_miss` | failover 换源重发 | 收口冷却，下请求换源 | 21600s（与 401/402/403 合并行） | HTTP 401/403 |

- 限频 3600s：文案语义"下个整点"，固定秒数保守覆盖（最坏多冷 59 分钟），不做
  动态整点计算。限频为 appkey 级（mcli 系共用同一 `appkey_file` 登录态）→
  同源 supply 连环撞、各自入冷却，最终落到 sankuai 系（不同 appkey），行为正确。
- 路由未命中 21600s：配置类错误，同 supply 重试必然复现 → 长冷却对标 401/403；
  **不做永久摘除**——mcli 侧路由策略可被管理员修复，长冷却+自动恢复符合
  "配置错误非硬件死亡"。
- 观测闭环：ACCESS `body_error=<code>` 字段 + log.warning + `status` 命令的
  cooldown 明细自动显示 `reason=body_*`；不新造账本（`StreamHealthStore` 口径
  不动——正文错误流 integrity=valid，属业务错误非协议完整性错误）。

### 2.6 明确不处理（边界声明）

- 流式**中途**嵌入错误句子（正常长流中出现的错误文本）：不判定——大正文无
  结构保护、误伤风险高；与"放行后不回头扫"一致。
- **纯文本流形态不识别（复核轻6，如实声明）**：流式判定依赖 observer 按 SSE
  事件驱动累计 text；若上游返回 200 + 非 SSE 纯文本 body，framer 解不出业务
  事件 → 累计 text 恒空 → 流式永不识别（退化现状）。该形态是否存在由 R1 取证
  确认；若实测为主形态，text 累计需加"非 SSE 兜底通道"再议。
- 预读闸门（提交前判定+当前请求换源）：**不做**，见 §1.3 / §3。

### 2.7 分期

- **Phase 1**：配置 + `match_body_error` 纯函数 + 非流式 PASSTHROUGH 判定/failover
  + 流式 PASSTHROUGH 旁路累计/收口冷却 + 单测 + 实测取证校准（用户全部 mcli
  supply 均此路径）。
- **Phase 2（暂缓，用户拍板 2026-10-10）**：转换路径非流式三处插点（结构同款）；
  count_tokens 插点（`:1824` JSON 校验失败处升级 body_error 判定）；转换流式
  三函数的 adapter text 累计（同语义）。

## 3. 风险与权衡

- **R1 wire 形态未取证（最大不确定）**：非流式路径覆盖 SSE text 与纯文本/JSON
  错误字段兜底（§2.3 提取器）；**流式仅覆盖 SSE text 形态**（纯文本流累计恒空
  不识别，见 §2.6）。实施前必须 curl 直打 mcli 复现（限频时段或人为触发），
  确认真实形态并校准 §1.5 假设。
- **R2 流式当前请求不救（B+ 边界的代价）**：流式撞正文错误时当前回复 = 一句
  错误文本，下一条请求才自愈。**用户已知情并接受（2026-10-10）**。若未来要
  "当前请求也换源"，唯一路径是重开预读闸门——与 2026-08-24 B+ 收敛裁决正面
  冲突（该机制曾因 9.6% 误杀被拆除）；届时须按 C 档教训先做误杀率评估
  （正文匹配无超时门槛，误杀来源与当年不同，但"预读族复杂度"风险同在）。
- **R3 误伤残余**：见 §2.2。非流式后果 = 一次换源重发；流式后果 = 该 supply
  冷却一段时间。均可恢复。阈值可调。
- **R4 文案变更失配**：mcli 升级改文案 → 规则失配退化为现状（错误文本透传、
  无冷却），fail-open 无新故障面。
- **决策已定（2026-10-10 用户拍板）**：① cooldown 采用合并式推荐形态（秒数随
  落地行归属，见 §2.1）；② 流式"当前请求不救"接受（R2）；③ Phase 2 暂缓。
  **仍为实施前置**：R1 wire 形态 curl 复现取证。

## 4. 验证方式

- **单测** `tests/test_body_error.py`（参照 `test_budget_retry.py` 假上游模式：
  patch `core.server.urllib.request.urlopen` 按队列返回假响应，驱动 `_forward` 全链路）：
  - 非流式 200+错误文本 → `cd.cooldown` 触发（code/秒数）、tried_set 轮转下一
    supply、客户端未收到错误文本、ACCESS `failover=1`；
  - 流式 200+错误文本（SSE text 形态）→ 客户端字节与无规则时完全一致（透传
    零改动回归）、`body_error=code`、cooldown 触发、下一请求换 supply；
  - 误伤防护：tool_use 回复带错误串 / 长正文含错误串 → 不触发；
  - 无 `body_error_rules` → 全行为与现状逐字节一致（零行为变化回归）；
  - 命中但 cooldown_rules 未配 → unconfigured 记账、不冷却；
  - 全 supply 耗尽（非流式）→ 503 + err_summary 含 `body_*`。
- **实测取证（前置）**：`curl -sS https://mcli.sankuai.com/v1/messages ...` 复现
  错误响应，确认 Content-Type 与 body 形态，回填 §1.5。
- **线上验证**：限频时段经 Claude Code 发请求，`model_proxy_cli.sh logs` 看
  `body_error=` 行、`status` 看 cooldown 明细（reason=body_rate_limited）；
